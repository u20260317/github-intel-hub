Панель у стилі «хакерського розвідувального центру», що працює на Cloudflare Workers: за розкладом обходить популярні репозиторії GitHub, за допомогою **рушія правил** (не ШІ) виконує оцінку популярності та розмітку точок навчання й підказує, які проєкти з відкритим кодом зараз стрімко зростають і чого варто навчитися в кожного з них. Щоранку «Президентський брифінг» автоматично надсилається в особисті повідомлення та в канал Telegram (канал розпізнається автоматично — достатньо зробити бота адміністратором, налаштування не потрібне).

Один файл `worker.js`, нуль залежностей, дані зберігаються в KV. Темна панель: майже чорний фон + неоновий зелений/ціан + моноширинний шрифт + текстура сканлайнів + рухомий рядок.

## Можливості

- **Одинадцять розвідувальних каналів** (у v2 додано 3, у v3 ще 2; за один раунд обходу — сумарно 11 викликів GitHub Search API, що значно нижче за ліміт у 50 підзапитів безкоштовного тарифу)
1. `surge` Зірки, що зростають: створені за останні 30 днів, stars>50
2. `trending-week` Хіти тижня: усталені популярні репозиторії з пушами за останні 7 днів, stars>5000
3. `ai-agent` AI/AGENT: ключові слова ai-agent / llm / mcp
4. `workers` Периферія/боти: cloudflare-workers / serverless / telegram-bot
5. `media` Генерація мультимедіа: comfyui / image-generation / text-to-speech
6. `devtools` Інструменти розробника: developer-tools / browser-automation / playwright
7. `security` ІБ · червона команда · SRC: cybersecurity / red team / bug bounty / penetration-testing / vulnerability, stars>200, пуші за останні 90 днів
8. `skills` Екосистема Skill: claude-skills / agent-skills / claude-skill (токени без лапок), stars>50, пуші за останні 90 днів
9. `creator` Повний набір для авторів: short-video / video-editing / ffmpeg / content creation / subtitles / livestream, stars>200
10. `src-hunt` SRC · пошук вразливостей (нове у v3): bug-bounty / 漏洞挖掘 / vulnerability-scanner / vulnerability-hunting, stars>30, пуші за останні 90 днів
11. `sec-learning` Навчальні матеріали з ІБ (нове у v3): pentest / ctf / web-security / cybersecurity-learning / security-roadmap, stars>200, пуші за останні 90 днів
- **Урок щодо синтаксису запитів (перевірено на практиці)**: у групі OR у дужках у GitHub Search можна розміщувати лише токени без лапок; фраза в лапках (наприклад, `"claude skills"`), поміщена всередину дужок OR, напряму повертає `total_count=0` (саме тому канал skills у v2 весь раунд був порожній). Фрази в лапках можна використовувати лише окремо, поза дужками, наприклад `"bug bounty" tools stars:>100` (54 записи, працює нормально). Ключові слова китайською допустимі, наприклад `漏洞挖掘 stars:>50` (47 записів).
- **Насіння точкового моніторингу WATCHLIST**: вручну відібраний список `SEEDS` у коді — сумарно 23 записи (екосистема Skill: 12 репозиторіїв + 1 зовнішній сайт Cocoloop, письмо — 3, наукові дослідження — 1, авторський контент — 8, ІБ — 2), у кожного — написана вручну одна фраза про точку навчання. На панелі є окремий розділ «Точковий моніторинг WATCHLIST», де записи згруповано за категоріями; якщо обхід знаходить однойменний репозиторій насіння, на картці об'єднується й показується його актуальний стан: ★ / популярність / рейтинг / приріст за раунд; насіння, що не потрапило в обхід, за ротацією окремо освіжається самим обходом (див. опис v5 нижче), а тим, до яких черга ще не дійшла, ставиться позначка «точковий моніторинг».
- **Порівняння знімків**: кожен раунд кількість зірок зберігається у знімок (KV `intel:prev`), на наступному раунді обчислюється приріст кожного репозиторію за раунд `starDelta`, на панелі — бейдж `+N★ за раунд`, список тих, що зростають, сортується за приростом.
- **Аналіз рушієм правил** (у коді це таблиця ключових слів `LEARNING_MAP` + зважена формула; на панелі чесно позначено «аналіз за правилами»)
- Оцінка популярності 0–100: масштаб зірок 40 + приріст за раунд 30 + свіжість пушів 20 + активність форків 10
- Теги точок навчання: 40 відображень ключових слів (у v2 додано: pentest/red-team → методика оцінки червоної команди, vulnerability → керування вразливостями, bug-bounty → підхід краудсорсингового тестування SRC, osint → розвідка з відкритих джерел, skill → патерн пакування Skill, subtitle → інженерія субтитрів, short-video → робочий процес коротких відео та ін.)
- Рейтинг: S ≥70, A ≥45, B — решта; до кожного запису — одна шаблонна оцінка, наприклад: «За останній раунд +320★, проєкт підключення за протоколом Python MCP — варто подивитися, як у нього влаштовано підключення за протоколом MCP».
- **Система деталізованих тегів безпеки** (нове у v3, у коді — `SECURITY_TAG_MAP`): за назвою репозиторію + описом + topics виконується ще один прохід зіставлення ключових слів безпеки, що дає деталізовані теги: SQL-ін'єкція / XSS / SSRF / RCE / змагання CTF / розвідка з відкритих джерел OSINT / аналіз шкідливого коду / цифрова криміналістика / захист синьої команди / аудит коду / проникнення у внутрішню мережу / підвищення привілеїв / сканування вразливостей / дослідження PoC / розбори вразливостей / траєкторія навчання / навчання із захисту від фішингу / зворотна інженерія / фазинг / DevSecOps та ін.; вони об'єднуються з тегами точок навчання з дедуплікацією, максимум 6 на репозиторій. Короткі слова RCE/PoC зіставляються за межами слів, щоб «source» помилково не позначався як RCE, а «epoch» — як PoC; «learning» позначається як траєкторія навчання лише в контексті безпеки, щоб репозиторії machine learning не отримували позначку помилково. Усі теги — класифікація, орієнтована на навчання/дослідження, а не посібник з експлуатації.
- **Взаємодія з панеллю** (оновлення v2): липка верхня панель із реальним годинником пекінського часу та статусом обходу; до KPI додано кількість каналів і кількість насіння; липка панель фільтрів підтримує двовимірну фільтрацію за каналом + рейтингом (S/A/B) і пошук; картки рейтингів — із рангами, анімованими смугами популярності та світінням при наведенні; кожна картка веде прямо на сторінку репозиторію на GitHub; кнопка негайного обходу з тротлінгом 30 хвилин.
- **Фільтрація за тегами та хмара тегів** (нове у v3): тег на кожній картці — клікабельний chip; клацання фільтрує «Усю розвідку» за цим тегом (комбінується з каналом/рейтингом/пошуком за AND), поруч із панеллю фільтрів — pill активного тега, що знімається одним клацанням; над розділом ІБ — хмара «популярних тегів»: за частотою тегів репозиторіїв трьох каналів безпеки (security/src-hunt/sec-learning) беруться перші 15, клацання по тегу в хмарі також запускає фільтрацію.
- **Пагінація «Усієї розвідки»** (нове у v3): сітку «Уся розвідка» переведено на клієнтську пагінацію — 24 записи на сторінку (відповідно до домовленості DEAL HUB), із кнопками «назад/уперед» і номерами сторінок (за великої кількості сторінок згортається трикрапкою); рядок стану показує «Сторінка X / Y · усього N записів (після фільтрації)»; будь-яка зміна фільтра/пошуку/тега повертає на сторінку 1 і перераховує кількість сторінок за відфільтрованим набором, а після перегортання сторінки вигляд автоматично прокручується до початку розділу «Уся розвідка». Розділи, як і раніше, показують Top-N без пагінації.

## Взаємодія з панеллю (v4)

- **Згортання розділів**: заголовки всіх основних розділів (список тих, що зростають, популярні нові зірки, розділ AI/AGENT, розділи за каналами, точковий моніторинг, уся розвідка) клікабельні — одне клацання згортає, ще одне розгортає (праворуч від заголовка індикатор ▼/▶ показує стан, розгортання — з анімацією плавної появи). У панелі фільтрів є кнопки одним натисканням «розгорнути все / згорнути все». За замовчуванням усе розгорнуто.
- **Розгорнути все всередині розділу**: за замовчуванням кожен розділ показує лише перші 6 карток; якщо їх більше, внизу є кнопка «Розгорнути всі N ▾» — клацання показує всі, повторне клацання по «Згорнути ▴» повертає як було. Це не те саме, що згортання розділу: згортання прибирає весь розділ цілком (увесь вміст під заголовком), а «розгорнути все» керує лише кількістю карток усередині розділу.
- **Подвійні елементи пагінації**: в «Усієї розвідки» елементи пагінації стоять **і над, і під** сіткою (стиль із помітною зеленою рамкою); номери сторінок, кнопки «назад/уперед» і рядок стану ділять один спільний стан — клацання по будь-якому набору синхронізує інший; 24 записи на сторінку, звичайна зв'язка з фільтрами за каналом/рейтингом/пошуком/тегом (зміна фільтра повертає на сторінку 1).
- **Президентський брифінг (плаваюче вікно)**: у правому нижньому куті постійно розташована плаваюча кнопка «📋 Президентський брифінг»; за клацанням відкривається вікно брифінгу, яке можна перетягувати (перетягування за рядок заголовка, підтримуються миша та дотики, за межі екрана не виїжджає; у правому верхньому куті — згорнути, ✕ — закрити, Esc також закриває; на маленьких екранах ширина автоматично підлаштовується під 92vw). Вміст сервер генерує з поточних даних за шаблоном правил: — зведення однією фразою + рядок популярності ключових слів,,, (включно з популярними тегами безпеки),, (з'являється, коли є перейменування репозиторіїв), (кількість насіння, що потрапило, та насіння-лідер); кожен запис клікабельний і веде на GitHub. У підвалі зазначено час генерації та позначку «рушій правил (згенеровано не ШІ)». Ті самі дані брифінгу вбудовано в сторінку і у вигляді JSON (`#brief-data`), а також їх можна отримати окремо через `GET /api/brief`.

## Нове у v5

- **Ротація свіжості насіння**: у кожному раунді обходу, окрім 11 пошукових викликів, витрачається ще не більше 3 викликів основного Repos API спеціально на освіження насіння, що «не потрапило в обхід цього раунду». Курсор зберігається в KV `intel:seedcursor` і йде списком насіння по порядку (пропускаючи ті, що потрапили), тож за кілька раундів усе насіння, що не потрапило, проходить ротацію. Результати освіження зберігаються в `intel:seedlive`: поточна повна назва / ★ / форки / час пуша + мітка часу освіження; свіжість даних картки насіння трирівнева — потрапляння в обхід цього раунду в реальному часі → окреме освіження (на картці позначка «окремо освіжено» та час) → статичний точковий моніторинг. Освіження йде через `GET /repos/{owner}/{repo}`: перейменований репозиторій перенаправляється на нову адресу, і відповідь — це його поточна ідентичність: панель показує поточну назву з позначкою «колишня X перейменована» й одночасно записує поточний id назад у `intel:seedids`; насінню, що повернуло 404, ставиться позначка «імовірно видалено / перейменування не відстежено». Верхня межа викликів GitHub за один раунд обходу = 11 пошуків + 3 освіження = 14 викликів.
- **Історія трендів тем**: кожен раунд обходу агрегує topics усіх репозиторіїв (за кожною темою: кількість репозиторіїв + сумарні зірки, залишаються лише перші 40 за сумарними зірками) і додає результат до KV `intel:topichist`, зберігаються лише останні 56 знімків (один раунд на 6 годин ≈ 14 днів). Методика тренду: порівняння з найближчим історичним знімком приблизно 24-годинної давності за приростом зірок/кількості репозиторіїв, а також обчислення «кількості раундів безперервного зростання» (від останнього знімка назад — кількість раундів, у яких сумарні зірки строго безперервно зростали). Перші 5 тем із додатним приростом зірок за 24 години потрапляють до Президентського брифінгу; в оглядовій зоні панелі під хмарою тегів є рядок трендів тем за тією самою методикою. Якщо історії менше двох раундів, блок автоматично приховується.
- **Щоденна розсилка Президентського брифінгу в Telegram**: після налаштування секретів, коли обхід за Cron завершується успішно й пекінський час уже пізніше 08:00, Президентський брифінг (тієї самої структури, що й вебверсія: обстановка за сьогодні / топ-3 тих, що зростають / топ-3 за популярністю / фокус ІБ / тренди тем / динаміка перейменувань + посилання на панель, формат HTML, у межах приблизно 1800 символів) надсилається в Telegram. Цілей розсилки може бути кілька одночасно: `TG_CHAT_ID` (особисті повідомлення боту), `TG_CHANNEL_ID` (вручну вказаний канал, можна заповнити `@назва_каналу` або числовий id `-100…`; з v5.3 це лише необов'язкове перекриття), а також усі автоматично зареєстровані у v5.3 канали (див. наступний пункт); усі використовують спільний `TG_BOT_TOKEN`; якщо цілей немає взагалі, функція мовчки вимикається. **Увага: під час розсилки в канал бот має бути адміністратором цього каналу, інакше Telegram відхилить публікацію.** Щоденний одноразовий шлюз оцінюється за кожною ціллю окремо, стан зберігається в `intel:briefpush` (з v5.3 формат — `{date, targets: {"dm"|"ch:<chatId>": {ok,ts}}}`; старий формат v5.2 і раніше `{date, dm, channel}` автоматично мігрує під час читання, й успішно мігровані записи, як і раніше, закривають шлюз цілі на цей день): ціль, у якої надсилання не вдалося, може автоматично повторитися в наступних обходах того самого дня, а успішно надіслана ціль цього дня повторно не надсилається. Ручний запуск: `POST /api/brief/push` (з v5.3.1 потребує автентифікації, див. нижче) надсилає одразу на всі цілі (особисті повідомлення + ручний канал + автоматично зареєстровані канали); тротлінг рахується за кожною ціллю окремо (у v5.3.1 KV `intel:pushmanual` — це відображення `{"dm"|"ch:<chatId>": ts}`, кожна ціль може бути вручну надіслана не більш ніж 1 раз за 6 годин; у щойно зареєстрованого каналу запису тротлінгу немає, тому йому можна одразу зробити додаткову розсилку, не чекаючи завершення тротлінгу інших цілей; мітка часу старого глобального формату під час читання автоматично мігрує в мітку лише для `dm`); поле `brief.push` у `GET /api/brief` повідомляє стан конфігурації (`configured: {dm, manualChannel, autoChannels}` — лише кількості, без назв каналів і повних id) та результати надсилання за кожною ціллю за сьогодні.
- **Автоматична реєстрація каналів (v5.3)**: більше не потрібно вручну дізнаватися id каналу й заповнювати `TG_CHANNEL_ID`. Після того як брифінгового бота призначено **адміністратором** будь-якого каналу, Telegram надсилає на Webhook оновлення `my_chat_member`, і Worker на його підставі реєструє канал у KV `intel:tgchannels` (`{ "<chatId>": {title, username, type, status, addedTs, updatedTs}}`), і канал автоматично стає ціллю щоденного брифінгу та ручної розсилки; коли бота знижують до звичайного учасника, видаляють або виганяють, канал позначається як `removed`, і розсилка на нього припиняється. У каналів, де бот був адміністратором ще до v5.3, такої події немає — вони додатково реєструються за **першим новим постом** у каналі (оновлення `channel_post`). `TG_CHANNEL_ID` і надалі може існувати як ручне перекриття паралельно з автоматичною реєстрацією; дедуплікація за chat id — надсилається лише одне повідомлення. У команді `/stats` **назви автоматично зареєстрованих каналів видимі лише власнику** (коли чат, що надіслав команду, — це сам `TG_CHAT_ID`), решта бачить лише кількість.
- **Повтор у разі збою каналу**: коли пошук за будь-яким каналом завершується помилкою (наприклад, 403 через неавтентифікований ліміт), через 2 секунди автоматично виконується один повтор, і лише після цього канал визнається невдалим; канали, що пройшли повтор, записуються до метаінформації обходу `meta.retriedChannels`; кількість освіженого насіння записується до `meta.seedRefreshed`.
- **Глобальний липкий стек**: рядок заголовка, рядок популярних тегів і панель фільтрів (канал/рейтинг/пошук/розгорнути-згорнути) об'єднано в один липкий стек (непрозорий фон), тому фільтрувати можна просто з будь-якої позиції прокрутки сторінки, а не лише всередині розділу «Уся розвідка»; всередині розділу «Уся розвідка» залишаються лише два набори елементів пагінації — верхній і нижній.

## Команди бота (v5.2)

Брифінговий бот (той самий бот, що й для щоденної розсилки) підтримує команди лише для читання: достатньо надіслати боту команду в Telegram; дані — з того самого джерела, що й у панелі (той самий набір KV); **усі команди лише читають і не виконують жодних управлінських дій** (не можна запустити обхід, не можна змінити конфігурацію).

| Команда | Опис |
|---|---|
| `/brief` | Президентський брифінг за сьогодні (той самий текст, що й у щоденній розсилці) |
| `/surge` | Топ-5 тих, що зростають (приріст зірок за цей раунд) |
| `/hot` | Топ-5 за популярністю |
| `/sec` | Фокус ІБ (топ-5 сімейства безпеки + популярні теги безпеки) |
| `/watchlist` | Статус точкового моніторингу (загальна кількість насіння, покриття обходом/освіженням/статикою, топ-5 за зірками, підказки про імовірно видалені та перейменовані) |
| `/stats` | Статус обходу (час останнього обходу, канали, нові за раунд, кількість освіженого насіння, конфігурація розсилки та дата останньої розсилки) |
| `/panel` | Посилання на панель розвідки та JSON брифінгу |
| `/help` (або `/start`) | Список команд |

Кроки підключення (поверх конфігурації розсилки v5 — ще три кроки):

1. Додайте Worker'у секрет `TG_WEBHOOK_SECRET`: згенеруйте випадковий рядок самостійно. Без цього секрету `POST /tg/webhook` напряму повертає 404, і система команд вважається вимкненою; після додавання всі запити, у яких заголовок `x-telegram-bot-api-secret-token` не збігається з ним, отримують 403.
2. Зареєструйте Webhook (замініть `<TOKEN>`, `<SECRET>` і домен на свої). **`allowed_updates` обов'язково має включати три типи: `message`, `my_chat_member`, `channel_post`**: перший — це команди, а останні два — джерела автоматичної реєстрації каналів у v5.3 (бота призначають адміністратором каналу або в уже зареєстрованому каналі з'являється новий пост — і канал реєструється); якщо останні два пропустити, команди працюватимуть як зазвичай, але канали автоматично не реєструватимуться:
`curl "https://api.telegram.org/bot<TOKEN>/setWebhook" -d "url=https://<ваша_адреса>/tg/webhook" -d "secret_token=<SECRET>" -d "allowed_updates=[\"message\",\"my_chat_member\",\"channel_post\"]"`
3. Зареєструйте меню команд: спочатку отримайте список — `curl https://<ваша_адреса>/api/tg/commands`, потім передайте повернутий масив `commands` як параметр `commands` під час виклику `setMyCommands` — і користувачі, набравши `/` у полі введення, побачать меню команд.

## Якір моніторингу: id репозиторію (v4)

Репозиторій можуть перейменувати або передати іншому власнику, тому `full_name` — нестабільний якір. З v4 кожен запис зберігає числовий `id` репозиторію GitHub (Search API повертає його як є), і вирівнювання виконується за ним:

- Знімок `intel:prev` переведено у формат із ключем за id: `{ts, byId: { "<id>": {s: кількість зірок, n: повна назва на той момент}}}`. Старий плоский формат `{full_name: stars}` мігрує автоматично: у раунді міграції зі старого знімка за назвами будується таблиця пошуку, і прирости рахуються як зазвичай, а після завершення обходу дані записуються вже в новому форматі.
- Під час вирівнювання за id для обчислення приросту, якщо id збігається, а повна назва змінилася, це визнається **перейменуванням**: приріст зберігається, на запис ставиться `renamedFrom`, до метаінформації обходу `meta.renames` додається запис `{from, to, stars}`, і подія з'являється в Президентського брифінгу.
- Для насіння точкового моніторингу окремо зберігається відображення id (KV `intel:seedids`, `{повна назва насіння: id}`, оновлюється кожен раунд обходу в разі потрапляння за назвою або за вже наявним id): після перейменування насіння воно в наступному раунді й далі знаходиться за id, а на панелі показуються його **поточна** повна назва та посилання.

## Кроки розгортання

1. У консолі Cloudflare створіть простір імен KV (наприклад, `github-intel-hub-data`).
2. Створіть новий Worker і вставте в нього повний текст `worker.js` (або розгорніть цей каталог через wrangler).
3. Прив'яжіть Worker'у KV: назва змінної обов'язково має бути **`INTEL_KV`** і вказувати на простір імен із кроку 1.
4. (Необов'язково) Додайте тригер Cron, рекомендовано `17 */6 * * *` (обхід кожні 6 годин; у неавтентифікованого GitHub низький ліміт — не частіть).
5. (Необов'язково) Додайте секрет `GITHUB_TOKEN`: GitHub Personal Access Token (достатньо лише читання публічних даних) помітно підвищує ліміт API; без нього теж працює.
6. (Необов'язково) Розсилка Президентського брифінгу в Telegram: додайте секрет `TG_BOT_TOKEN` (токен від BotFather), потім додайте `TG_CHAT_ID` (ваш id особистого чату); якщо потрібен інтерфейс ручної розсилки `POST /api/brief/push`, додайте ще секрет `PUSH_KEY` (згенеруйте випадковий рядок самостійно та під час виклику передавайте його в заголовку `x-push-key`; без цього секрету інтерфейс напряму закрито з 403); для цілей-каналів id вручну налаштовувати не потрібно — після підключення Webhook за розділом «Команди бота (v5.2)» (включно з `my_chat_member`/`channel_post`) достатньо призначити бота адміністратором каналу, і він зареєструється автоматично (v5.3), а `TG_CHANNEL_ID` (канал `@username` або числовий id `-100…`) слугує лише необов'язковим ручним перекриттям. Під час розсилки в канал бот має бути адміністратором цього каналу. Якщо нічого не додавати — розсилки не буде. Якщо потрібно ще й підключити команди бота, додайте секрет `TG_WEBHOOK_SECRET` і зареєструйте Webhook та меню команд за розділом «Команди бота (v5.2)».
7. Відкрийте адресу Worker'а й натисніть «Негайний обхід», щоб підтягнути першу порцію даних; або виконайте `curl -X POST https://<ваша_адреса>/api/refresh`.

## Інтерфейси

| Маршрут | Опис |
|---|---|
| `GET /` | Панель розвідки (HTML) |
| `GET /api/repos` | JSON репозиторіїв останнього раунду (включно з heat/grade/learnTags/verdict/starDelta), із приєднаними об'єднаними даними насіння `watchlist` |
| `GET /api/watchlist` | JSON списку насіння точкового моніторингу (включно з категорією кожного запису, вручну написаною точкою навчання та даними потрапляння в реальному часі `live`; за непотрапляння — `null`) |
| `GET /api/stats` | Метаінформація останнього раунду обходу (час, кількість записів за каналами, помилки, події перейменувань `renames`) |
| `GET /api/brief` | JSON Президентського брифінгу (ті самі дані, що й у плаваючого вікна панелі: обстановка, топ-3 тих, що зростають / за популярністю, фокуси ІБ/Skill, динаміка перейменувань, популярність ключових слів, тренди тем, динаміка точкового моніторингу), із приєднаним статусом розсилки `brief.push` (кількості `configured: {dm, manualChannel, autoChannels}` та результати за кожною ціллю за сьогодні, без назв каналів / повних id) |
| `POST /api/brief/push` | Ручна розсилка Президентського брифінгу на цілі TG (особисті повідомлення + ручний канал + автоматично зареєстровані канали). Потрібен секрет `PUSH_KEY`: якщо не налаштовано — 403 `status: "push_disabled"`, якщо заголовок `x-push-key` відсутній/невірний — 401 `status: "unauthorized"` (без розсилки та без запису тротлінгу); після успішної автентифікації тротлінг 6 годин застосовується за кожною ціллю окремо, надсилання йде лише на цілі, не зачеплені тротлінгом, відповідь містить `targets` (ключі цілей цієї розсилки) та `skipped` (ключі цілей, пропущених через тротлінг); за відсутності цілей повертається `status: "not_configured"` |
| `GET /api/tg/commands` | JSON списку команд бота (для `setMyCommands`, 8 команд) |
| `POST /tg/webhook` | Точка входу Webhook Telegram (команди бота лише для читання + автоматична реєстрація каналів; потрібен секрет `TG_WEBHOOK_SECRET`, без нього — 404, за невірного секрету — 403) |
| `POST /api/refresh` | Ручний запуск обходу; повторні виклики протягом 30 хвилин тротляться (повертається `throttled: true`) |
| Cron `scheduled()` | Обхід за розкладом, ручний тротлінг не застосовується |

Ключі KV: `intel:latest` (останні дані), `intel:prev` (знімок зірок минулого раунду; з v4 — формат із ключем за id), `intel:meta` (метаінформація обходу), `intel:seedids` (відображення id репозиторіїв насіння), `intel:seedcursor` (курсор ротації свіжості насіння), `intel:seedlive` (результати освіження насіння), `intel:topichist` (історичні знімки трендів тем, останні 56), `intel:briefpush` (стан щоденної розсилки брифінгу; з v5.3 — `{date, targets}` із записами за ключами цілей), `intel:pushmanual` (тротлінг ручної розсилки; з v5.3.1 — відображення за цілями `{"dm"|"ch:<chatId>": ts}`, старий глобальний формат мігрує під час читання), `intel:tgchannels` (таблиця автоматично зареєстрованих каналів, нове у v5.3).

## Чесно про дані

- Єдине джерело даних — публічні результати пошуку GitHub Search API; порядок сортування та критерії включення визначає GitHub; запити каналів — це правила за ключовими словами, а не офіційний GitHub Trending.
- **Для приросту зірок потрібно щонайменше два раунди обходу**: у першому раунді приріст в усіх репозиторіїв порожній, і в оцінці буде написано «новий у базі розвідки»; `+N★` з'являється лише з другого раунду.
- Ліміт неавтентифікованих викликів дуже низький (Search API — близько 10 разів на хвилину, плюс погодинна квота); 11 викликів за раунд — нормально, але не оновлюйте вручну надто часто — у коді вже зроблено тротлінг 30 хвилин.
- Якщо захоплення каналу не вдалося, цей канал позначається як аномальний у рухомому рядку панелі, і використовуються старі дані цього каналу з минулого раунду — уся картина даних не стирається; якщо не вдалися всі канали, наявні дані не перезаписуються.
- Оцінки, рейтинги й точки навчання — цілком результат правил і можуть бути хибними (наприклад, репозиторії, що «примазалися» до ключових слів в описі); це лише орієнтир для відбору, а не гарантія висновку «варто вивчати».
- KV — сховище з підсумковою узгодженістю (eventual consistency); протягом кількох десятків секунд одразу після запису обходу панель може короткочасно читати старі дані — це нормальне явище.
