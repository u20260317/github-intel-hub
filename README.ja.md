Cloudflare Workers 上で動作する「ハッカー情報センター」風パネルです。GitHub の人気リポジトリを定時巡回し、**ルールエンジン**（AI ではありません）で人気度を分析して学習ポイントを付け、最近どのオープンソースプロジェクトが急上昇しているか、それぞれ何を学ぶ価値があるかを伝えます。毎朝の「大統領ブリーフィング」は Telegram の個人チャットとチャンネルへ自動送信されます（チャンネルで Bot を管理者にすると自動認識され、設定不要です）。

単一ファイル `worker.js`、依存関係なし、データは KV に保存します。ダークなパネル：ほぼ黒の背景 + ネオングリーン／シアン + 等幅フォント + スキャンラインの質感 + ティッカー。

## 機能

- **11 の情報チャンネル**（v2 で 3 件追加、v3 でさらに 2 件追加；1 回の巡回で GitHub Search API を 11 回呼び、無料版の 50 サブリクエスト上限を大きく下回ります）
1. `surge` 急上昇する新星：過去 30 日以内に作成され、stars>50
2. `trending-week` 今週の人気：過去 7 日以内にプッシュがあり、stars>5000 の老舗人気リポジトリ
3. `ai-agent` AI/AGENT：ai-agent / llm / mcp キーワード
4. `workers` エッジ/Bot：cloudflare-workers / serverless / telegram-bot
5. `media` マルチメディア生成：comfyui / image-generation / text-to-speech
6. `devtools` 開発ツール：developer-tools / browser-automation / playwright
7. `security` サイバーセキュリティ・レッドチーム・SRC：cybersecurity / red team / bug bounty / penetration-testing / vulnerability、stars>200、過去 90 日以内にプッシュ
8. `skills` Skill エコシステム：claude-skills / agent-skills / claude-skill（引用符なし token）、stars>50、過去 90 日以内にプッシュ
9. `creator` セルフメディア一式：short-video / video-editing / ffmpeg / content creation / subtitles / livestream、stars>200
10. `src-hunt` SRC・脆弱性探し（v3 で追加）：bug-bounty / 漏洞挖掘 / vulnerability-scanner / vulnerability-hunting、stars>30、過去 90 日以内にプッシュ
11. `sec-learning` サイバーセキュリティ学習資料（v3 で追加）：pentest / ctf / web-security / cybersecurity-learning / security-roadmap、stars>200、過去 90 日以内にプッシュ
- **クエリ構文の教訓（実測）**：GitHub Search の OR 括弧グループには引用符なし token しか入れられません。引用符付きフレーズ（例：`"claude skills"`）を OR 括弧に入れると、直接 `total_count=0` が返ります（v2 の skills チャンネルはこのため 1 ラウンド丸ごと空でした）。引用符付きフレーズは括弧の外で単独に使うしかありません。例：`"bug bounty" tools stars:>100`（54 件、正常）。中国語キーワードも使えます。例：`漏洞挖掘 stars:>50`（47 件）。
- **重点監視シード WATCHLIST**：コード内の `SEEDS` にある手作業で選んだリスト全 23 件（Skill エコシステム 12 リポジトリ + 外部サイト Cocoloop 1 件、執筆 3、科学研究 1、セルフメディア 8、サイバーセキュリティ 2）で、各項目に手書きの学習ポイントが 1 文付いています。パネルには独立した「重点監視 WATCHLIST」セクションがあり、カテゴリ別にグループ表示されます。巡回で同名リポジトリに当たったシードは、カードにリアルタイムの ★／人気度／評価／今回の増加分が統合表示されます。当たらなかったシードは巡回が「個別の鮮度維持」として順番に取得します（下記の v5 の説明を参照）。まだ順番が回ってきていないものには「指名監視中」と表示されます。
- **スナップショット比較**：ラウンドごとにスター数をスナップショット（KV `intel:prev`）へ保存し、次ラウンドで各リポジトリの今回の増加分 `starDelta` を計算します。パネルには `+N★ 今回` バッジがあり、急上昇ランキングは増加分で並べ替えます。
- **ルールによる分析**（コード内は `LEARNING_MAP` キーワード表 + 重み付け式で、パネルには「ルールによる分析」と正直に表示します）
- 人気度スコア 0-100：スター規模 40 + 今回の増加分 30 + プッシュの新しさ 20 + fork の活発さ 10
- 学習ポイントタグ：40 件のキーワードマッピング（v2 で追加された pentest/red-team→レッドチーム評価手法、vulnerability→脆弱性管理、bug-bounty→SRC クラウドテストの考え方、osint→オープンソースインテリジェンス、skill→Skill カプセル化パターン、subtitle→字幕エンジニアリング、short-video→ショート動画ワークフローなど）
- 評価：S ≥70、A ≥45、B はその他。各項目にテンプレート分析が 1 文付きます。例：「直近ラウンドで +320★、Python の MCP プロトコル接続プロジェクトで、その MCP プロトコル接続を見る価値があります。」
- **セキュリティ詳細タグ体系**（v3 で追加、コード内は `SECURITY_TAG_MAP`）：リポジトリ名＋説明＋topics に対してもう 1 回セキュリティキーワードマッチングを行い、SQL インジェクション / XSS / SSRF / RCE / CTF 競技 / オープンソースインテリジェンス OSINT / マルウェア解析 / デジタルフォレンジック / ブルーチーム防御 / コード監査 / 内部ネットワーク侵入 / 権限昇格 / 脆弱性スキャン / PoC 研究 / 脆弱性レビュー / 学習ロードマップ / フィッシング防御演習 / リバースエンジニアリング / ファジング / DevSecOps などの詳細タグを生成し、学習ポイントタグと統合・重複除去して、1 リポジトリあたり上限 6 個にします。短い語 RCE/PoC は単語境界でマッチングし、「source」を RCE と誤判定したり、「epoch」を PoC と誤判定したりしないようにします。「learning」はセキュリティ文脈でのみ学習ロードマップとしてタグ付けし、machine learning リポジトリへの誤判定を避けます。タグはいずれも学習／研究向けの分類であり、悪用ガイドではありません。
- **パネル操作**（v2 でアップグレード）：スティッキーなトップバーに北京時間のリアルタイム時計と巡回ステータスを表示。KPI にチャンネル数とシード数を追加。スティッキーなフィルターバーはチャンネル + 評価（S/A/B）の二次元フィルターと検索に対応。各ランキングのカードには順位、人気度バーのアニメーション、ホバー時のグローがあり、各カードから GitHub リポジトリページへ直接移動できます。今すぐ巡回ボタンには 30 分のスロットリングがあります。
- **タグフィルターとタグクラウド**（v3 で追加）：各カードのタグはクリック可能な chip で、クリックするとそのタグで「全情報」をフィルターします（チャンネル／評価／検索と AND で組み合わせ）。フィルターバーの横には有効なタグの pill があり、ワンクリックで解除できます。サイバーセキュリティ専用エリアの上には「人気タグ」クラウドがあり、セキュリティ 3 チャンネル（security/src-hunt/sec-learning）のリポジトリのタグ頻度から上位 15 件を取り、クラウド内のタグをクリックしても同様にフィルターが発動します。
- **全情報のページネーション**（v3 で追加）：「全情報」グリッドはクライアント側ページネーションに変わり、1 ページ 24 件（DEAL HUB の規約と一致）、前へ／次へとページ番号ボタン（ページ数が多い場合は省略記号で折りたたみ）があり、ステータス行には「X / Y ページ · 全 N 件（フィルター後）」と表示されます。フィルター／検索／タグが変わるたびに 1 ページ目に戻り、フィルター後の集合でページ数を再計算します。ページをめくると自動的に「全情報」エリアの先頭へスクロールバックします。各専用エリアは従来どおり Top-N 表示で、ページネーションしません。

## パネル操作（v4）

- **セクション折りたたみ**：主要セクション（急上昇ランキング、人気の新星、AI/AGENT 専用エリア、各チャンネル専用エリア、重点監視、全情報）すべてのタイトルバーがクリック可能で、1 回クリックで折りたたみ、もう 1 回で展開します（タイトル右側の ▼/▶ が状態を示し、展開時にはフェードインのトランジションアニメーションがあります）。フィルターバーには「すべて展開 / すべて折りたたみ」のワンクリックボタンがあります。デフォルトはすべて展開です。
- **セクション内のすべて展開**：各専用エリアはデフォルトで最初の 6 枚のカードだけを表示し、それを超える場合は下部に「すべて N 件を展開 ▾」ボタンがあり、クリックすると全部が見え、再度「折りたたむ ▴」をクリックすると元に戻ります。セクション折りたたみとは別物です：折りたたみはセクション全体（タイトル以下の全コンテンツ）を畳み、すべて展開は専用エリア内のカード数だけを制御します。
- **二重ページネーションコントロール**：「全情報」のページネーションコントロールはグリッドの**上と下に 1 セットずつ**あり（目立つ緑の枠線スタイル）、ページ番号、前へ／次へ、ステータス行が同じ状態を共有し、どちらを操作してももう一方に同期します。1 ページ 24 件で、チャンネル／評価／検索／タグフィルターとも従来どおり連動します（フィルターが変わると 1 ページ目に戻ります）。
- **大統領ブリーフィング（フローティングウィンドウ）**：右下に常駐する「📋 大統領ブリーフィング」フローティングボタンを開くと、ドラッグ可能なブリーフィングウィンドウが表示されます（タイトルバーを押さえてドラッグ、マウスとタッチに対応、画面の境界の外には出ません。右上の — で最小化、✕ で閉じ、Esc でも閉じられます。小さい画面では自動的に 92vw 幅に適応します）。内容はサーバー側が現在のデータからルールテンプレートで生成します：1 文の総括 + キーワード人気度を 1 行、、、（人気のセキュリティタグを含む）、、（リポジトリのリネームがある場合に表示）、（シードのヒット数とトップシード）で、各項目から GitHub へ移動できます。フッターには生成時刻と「ルールエンジン（AI 生成ではありません）」と明記されます。同じブリーフィングデータは JSON 形式でもページに埋め込まれており（`#brief-data`）、`GET /api/brief` から単独で取得することもできます。

## v5 の新機能

- **シード鮮度維持ローテーション**：各巡回ラウンドでは 11 回の検索に加えて、最大 3 回までコア Repos API 呼び出しを追加で使い、「今回の巡回で当たらなかった」シード専用の鮮度維持を行います。カーソルは KV `intel:seedcursor` に保存し、シードリストの順序でローテーションします（当たったものはスキップ）。数ラウンドで当たらなかったシード全部を一巡できます。鮮度維持の結果は `intel:seedlive` に保存します：現在のフルネーム／★／fork／プッシュ時刻 + 鮮度維持タイムスタンプ。シードカードのデータ鮮度は 3 段階です——今回の巡回でリアルタイムにヒット → 個別の鮮度維持（カードに「個別の鮮度維持」マークと時刻が付く）→ 静的な指名。鮮度維持は `GET /repos/{owner}/{repo}` を使い、リネームされたリポジトリは新しいアドレスへリダイレクトされ、レスポンスがそのまま現在の身元になります：パネルには現在の名前が表示され「元 X からリネーム」と注記され、同時に現在の id が `intel:seedids` へ書き戻されます。404 が返るシードには「削除された可能性／リネーム未追跡」と注記されます。1 回の巡回の GitHub 呼び出し上限 = 11 検索 + 3 鮮度維持 = 14 回です。
- **トピックトレンド履歴**：各巡回ラウンドで全リポジトリの topics を集計し（トピックごと：リポジトリ数 + 累計スター、累計スター上位 40 のみ残す）、KV `intel:topichist` へ追加します。最近 56 スナップショットのみ保持します（6 時間に 1 ラウンド ≈ 14 日分）。トレンドの口径：約 24 時間前に最も近い過去のスナップショットとスター数／リポジトリ数の増加分を比較し、「連続上昇ラウンド数」（最新スナップショットから遡って、累計スターが連続して厳密に増加したラウンド数）を計算します。24h スター増加分が正の上位 5 トピックが大統領ブリーフィングのに入り、パネルの総覧エリアのタグクラウドの下にも同じ口径のトピックトレンドが 1 行表示されます。履歴が 2 ラウンド未満の場合は自動的に隠れます。
- **大統領ブリーフィングの Telegram 毎日送信**：Secret を設定すると、Cron 巡回が成功し、北京時間が 08:00 を過ぎているときに、大統領ブリーフィング（Web 版と同じ構成：今日の情勢／急上昇 TOP3／人気 TOP3／サイバーセキュリティ焦点／トピックトレンド／リネーム動向 + パネルリンク、HTML 形式、約 1800 字以内）を Telegram へ送信します。送信先は複数同時に存在できます：`TG_CHAT_ID`（Bot 個人チャット）、`TG_CHANNEL_ID`（手動指定のチャンネル。`@チャンネル名` または `-100…` の数字 id を記入でき、v5.3 以降は任意の上書きに過ぎません）、それに v5.3 で自動登録された全チャンネル（次項参照）で、`TG_BOT_TOKEN` を共用します。送信先が 1 つもなければ機能は静かにオフになります。**注意：チャンネルへ送信する際、Bot はそのチャンネルの管理者でなければならず、そうでないと Telegram が投稿を拒否します。** 1 日 1 回のゲートは送信先ごとに判定し、状態は `intel:briefpush` に保存します（v5.3 以降は `{date, targets: {"dm"|"ch:<chatId>": {ok,ts}}}`。v5.2 以前の `{date, dm, channel}` という旧形式は読み取り時に自動移行され、移行された成功記録はそのまま当日その送信先のゲートとして機能します）：ある送信先が失敗したら当日の後続の巡回で自動的に再試行でき、成功済みの送信先は当日に再送されません。手動トリガー：`POST /api/brief/push`（v5.3.1 以降は認証が必要。下記参照）で全送信先（個人チャット + 手動チャンネル + 自動登録チャンネル）へ一度に送信します。スロットリングは送信先ごとに計算します（KV `intel:pushmanual` は v5.3.1 以降 `{"dm"|"ch:<chatId>": ts}` マップで、各送信先は 6 時間に最大 1 回まで手動送信できます。新規登録チャンネルにはスロットリング記録がないため、他の送信先のスロットリング期限を待たずにすぐ補完送信できます。旧来の全体形式のタイムスタンプは読み取り時に `dm` のみのスタンプへ自動移行されます）。`GET /api/brief` の `brief.push` フィールドは設定状態（`configured: {dm, manualChannel, autoChannels}`、チャンネルのタイトルや完全な id は含まず件数のみ）と、今日の各送信先の送信結果を返します。
- **チャンネル自動登録（v5.3）**：もうチャンネル id を手動で調べて `TG_CHANNEL_ID` に記入する必要はありません。ブリーフィング Bot を任意のチャンネルの**管理者**にすると、Telegram が Webhook へ `my_chat_member` 更新を送り、Worker はそれに基づきチャンネルを KV `intel:tgchannels`（`{ "<chatId>": {title, username, type, status, addedTs, updatedTs}}`）へ登録し、自動的に毎日ブリーフィングと手動送信の送信先になります。Bot が通常メンバーへ降格されたり、除去されたり、追放されたりすると、そのチャンネルは `removed` とマークされ送信が止まります。v5.3 より前にすでに管理者だったチャンネルにはこのイベントがないため、そのチャンネルでの**最初の新しい投稿**（`channel_post` 更新）で補完登録されます。`TG_CHANNEL_ID` は手動上書きとして自動登録と併存でき、chat id で重複除去して 1 通だけ送ります。`/stats` コマンドでは、自動登録チャンネルの**タイトルはオーナーにだけ見えます**（発令 chat が `TG_CHAT_ID` 本人の場合）。他の人には件数だけが見えます。
- **チャンネル失敗時の再試行**：いずれかのチャンネルの検索でエラー（例：未認証枠の 403）が起きた場合、2 秒空けて自動的に 1 回再試行してから失敗と判定します。再試行したチャンネルは巡回メタ情報 `meta.retriedChannels` に記録されます。シード鮮度維持数は `meta.seedRefreshed` に記録されます。
- **全体スティッキースタック**：タイトルバー、人気タグ行、フィルターバー（チャンネル／評価／検索／展開・折りたたみ）は 1 つのスティッキースタック（不透明な背景）に統合され、ページのどのスクロール位置からでも直接フィルターできるようになりました。「全情報」エリア内だけのものではなくなりました。「全情報」エリア内には上下 2 セットのページネーションコントロールだけが残ります。

## Bot コマンド（v5.2）

ブリーフィング Bot（毎日送信と同じ Bot）は読み取り専用コマンドに対応します：Telegram で Bot にコマンドを送るだけです。データはパネルと同源（同じ KV 群）で、**すべて読み取り専用で、管理アクションは一切しません**（巡回をトリガーできず、設定も変更できません）。

| コマンド | 説明 |
|---|---|
| `/brief` | 今日の大統領ブリーフィング（毎日送信と同一のテキスト） |
| `/surge` | 急上昇ランキング TOP5（今回のスター増加分） |
| `/hot` | 人気ランキング TOP5 |
| `/sec` | サイバーセキュリティ焦点（セキュリティファミリー TOP5 + 人気セキュリティタグ） |
| `/watchlist` | 重点監視ステータス（シード総数、巡回／鮮度維持／静的カバー、スター TOP5、削除の可能性とリネームのヒント） |
| `/stats` | 巡回ステータス（前回巡回時刻、チャンネル、今回の新規追加、シード鮮度維持数、送信設定と直近の送信日） |
| `/panel` | 情報パネルとブリーフィング JSON へのリンク |
| `/help`（または `/start`） | コマンド一覧 |

開通手順（v5 の送信設定に加えて 3 ステップ）：

1. Worker に Secret `TG_WEBHOOK_SECRET` を追加します：自分でランダムな文字列を生成してください。この Secret がない場合、`POST /tg/webhook` は直接 404 を返し、コマンドシステムはオフ同然です。追加後は、リクエストヘッダー `x-telegram-bot-api-secret-token` がそれと一致しないリクエストはすべて 403 になります。
2. Webhook を登録します（`<TOKEN>`、`<SECRET>`、ドメインを自分のものに置き換えてください）。**`allowed_updates` には `message`、`my_chat_member`、`channel_post` の 3 種類を必ず含めてください**：1 つ目はコマンド用、後 2 つは v5.3 のチャンネル自動登録の発生源です（Bot がチャンネル管理者に設定されたとき、または登録済みチャンネルに新しい投稿があったときにチャンネルを登録します）。後 2 つを欠くと、コマンドは通常どおり動作しますが、チャンネルは自動登録されません：
`curl "https://api.telegram.org/bot<TOKEN>/setWebhook" -d "url=https://<あなたのアドレス>/tg/webhook" -d "secret_token=<SECRET>" -d "allowed_updates=[\"message\",\"my_chat_member\",\"channel_post\"]"`
3. コマンドメニューを登録します：まず一覧を取得します `curl https://<あなたのアドレス>/api/tg/commands`。返された `commands` 配列を `commands` パラメータとして `setMyCommands` を呼ぶと、ユーザーが入力欄で `/` を打ったときにコマンドメニューが見えるようになります。

## 監視アンカー：リポジトリ id（v4）

リポジトリはリネームされたり所有者が移転したりするため、`full_name` は安定したアンカーではありません。v4 以降、各レコードには GitHub の数字リポジトリ `id`（Search API がそのまま返すもの）を保存し、それを基準に突き合わせます：

- スナップショット `intel:prev` は id キー形式 `{ts, byId: { "<id>": {s: スター数, n: 当時のフルネーム}}}` に変わりました。旧来のフラットな `{full_name: stars}` 形式は自動移行されます：移行ラウンドではまず旧スナップショットで名前引きのルックアップ表を作り、通常どおり増加分を計算し、巡回終了時に新しい形式で書き戻します。
- id で突き合わせて増加分を計算する際、id が同じでフルネームが変わっていたら、**リネーム**と判定します：増加分は保持され、レコードに `renamedFrom` が付き、巡回メタ情報 `meta.renames` に `{from, to, stars}` が 1 件記録され、大統領ブリーフィングのに現れます。
- 重点監視シードは別途 id マッピングを保存します（KV `intel:seedids`、`{シードのフルネーム: id}`、各巡回ラウンドで名前または既存 id で当たったときに更新）：シードがリネームされた後も次ラウンドでは id で当たり、パネルにはその**現在**のフルネームとリンクが表示されます。

## デプロイ手順

1. Cloudflare コンソールで KV namespace を作成します（例：`github-intel-hub-data`）。
2. Worker を新規作成し、`worker.js` の全文を貼り付けます（または wrangler でこのディレクトリをデプロイします）。
3. Worker に KV をバインドします：変数名は必ず **`INTEL_KV`** とし、手順 1 の namespace を指すようにします。
4. （任意）Cron トリガーを追加します。推奨は `17 */6 * * *`（6 時間に 1 回巡回。未認証の GitHub 枠は低いため、頻繁にしすぎないでください）。
5. （任意）Secret `GITHUB_TOKEN` を追加します：GitHub Personal Access Token（公開データの読み取り専用で可）を入れると API 枠を大幅に増やせます。入れなくても動作します。
6. （任意）大統領ブリーフィングの Telegram 送信：Secret `TG_BOT_TOKEN`（BotFather が発行した token）を追加し、さらに `TG_CHAT_ID`（あなたの個人チャット id）を追加します。手動送信インターフェース `POST /api/brief/push` を使う場合は、さらに Secret `PUSH_KEY` を追加します（自分でランダムな文字列を生成し、呼び出し時にリクエストヘッダー `x-push-key` に入れます。この Secret がない場合、そのインターフェースは直接 403 で閉じられます）。チャンネルの送信先は id を手動設定する必要はありません——「Bot コマンド（v5.2）」の節に従って Webhook（`my_chat_member`/`channel_post` を含む）を開通した後、Bot をチャンネル管理者にすれば自動登録されます（v5.3）。`TG_CHANNEL_ID`（チャンネルの `@ユーザー名` または `-100…` の数字 id）は任意の手動上書きとしてのみ使います。チャンネルへ送信する際、Bot はそのチャンネルの管理者でなければなりません。どちらも追加しなければ送信されません。Bot コマンドも開通する場合は、さらに Secret `TG_WEBHOOK_SECRET` を追加し、「Bot コマンド（v5.2）」の節に従って Webhook とコマンドメニューを登録します。
7. Worker のアドレスを開き、「今すぐ巡回」をクリックして最初のデータを取得します。または `curl -X POST https://<あなたのアドレス>/api/refresh` を実行します。

| ルート | 説明 |
|---|---|
| `GET /` | 情報パネル（HTML） |
| `GET /api/repos` | 最新の 1 批のリポジトリ JSON（heat/grade/learnTags/verdict/starDelta を含む）。`watchlist` シードの統合データも付きます |
| `GET /api/watchlist` | 重点監視シードリスト JSON（各項目のカテゴリ、手書きの学習ポイント、リアルタイムのヒットデータ `live` を含み、当たらなかったものは `null`） |
| `GET /api/stats` | 直近 1 ラウンドの巡回メタ情報（時刻、各チャンネルの件数、エラー、リネームイベント `renames`） |
| `GET /api/brief` | 大統領ブリーフィング JSON（パネルのフローティングウィンドウと同じデータ：情勢、急上昇／人気 TOP3、サイバーセキュリティ／Skill 焦点、リネーム動向、キーワード人気度、トピックトレンド、重点監視動向）。`brief.push` の送信状態（`configured: {dm, manualChannel, autoChannels}` の件数と今日の各送信先の結果、チャンネルのタイトル／完全な id は含みません）も付きます |
| `POST /api/brief/push` | 大統領ブリーフィングを TG 送信先（個人チャット + 手動チャンネル + 自動登録チャンネル）へ手動送信します。Secret `PUSH_KEY` が必要です：未設定の場合は 403 で `status: "push_disabled"` を返し、リクエストヘッダー `x-push-key` が欠けている／間違っている場合は 401 で `status: "unauthorized"` を返します（送信せず、スロットリングも書き込みません）。認証が通った後は送信先ごとに 6 時間のスロットリングを行い、スロットリングされていない送信先にだけ送信します。レスポンスには `targets`（今回送信した送信先キー）と `skipped`（スロットリングでスキップした送信先キー）が含まれ、送信先がない場合は `status: "not_configured"` を返します |
| `GET /api/tg/commands` | Bot コマンドリスト JSON（`setMyCommands` 用、8 件） |
| `POST /tg/webhook` | Telegram Webhook の入口（Bot 読み取り専用コマンド + チャンネル自動登録。Secret `TG_WEBHOOK_SECRET` が必要で、未設定の場合は 404、キーが間違っている場合は 403 を返します） |
| `POST /api/refresh` | 巡回を手動でトリガーします。30 分以内の繰り返し呼び出しはスロットリングされます（`throttled: true` を返します） |
| Cron `scheduled()` | 定時巡回。手動スロットリングは適用されません |

KV キー：`intel:latest`（最新データ）、`intel:prev`（前ラウンドのスター数スナップショット。v4 以降は id キー形式）、`intel:meta`（巡回メタ情報）、`intel:seedids`（シードリポジトリ id マッピング）、`intel:seedcursor`（シード鮮度維持ローテーションカーソル）、`intel:seedlive`（シード鮮度維持結果）、`intel:topichist`（トピックトレンド履歴スナップショット、最近 56 件）、`intel:briefpush`（ブリーフィング毎日送信の状態。v5.3 以降は `{date, targets}` で送信先キーごとに記録）、`intel:pushmanual`（手動送信スロットリング。v5.3.1 以降は送信先ごとのマップ `{"dm"|"ch:<chatId>": ts}` で、旧来の全体形式は読み取り時に移行）、`intel:tgchannels`（自動登録されたチャンネル表。v5.3 で追加）。

## データの誠実さに関する説明

- データソースは GitHub Search API の公開検索結果のみで、並び順と収録の口径は GitHub が決めます。チャンネルクエリはキーワードルールであり、GitHub 公式の Trending ではありません。
- **スター増加分には少なくとも 2 ラウンドの巡回が必要です**：1 ラウンド目は全リポジトリの増加分が空で、分析には「情報データベースに新規登録」と書かれます。2 ラウンド目から `+N★` が出ます。
- 未認証呼び出しの枠はとても低いです（Search API は約 10 回/分で、1 時間あたりのクォータもあります）。1 ラウンド 11 回の呼び出しは問題ありませんが、高頻度に手動リフレッシュしないでください——コードにはすでに 30 分のスロットリングがあります。
- あるチャンネルの取得が失敗した場合、そのチャンネルはパネルのティッカーで異常とマークされ、前ラウンドのそのチャンネルの古いデータを引き続き使い、データ全体を消すことはありません。全チャンネルが失敗した場合は既存データを上書きしません。
- 分析、評価、学習ポイントはすべてルールの産物であり、誤判定の可能性があります（例：説明文にキーワードを寄せたリポジトリ）。絞り込みの参考に過ぎず、「学ぶ価値がある」という結論を保証するものではありません。
- KV は結果整合性ストレージです。巡回が書き終えた直後の数十秒間、パネルが一時的に古いデータを読むことがありますが、正常な現象です。
