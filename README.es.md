Un panel con estilo de «centro de inteligencia hacker» que se ejecuta en Cloudflare Workers: barre periódicamente los repositorios populares de GitHub, utiliza un **motor de reglas** (no IA) para evaluar su impulso y anotar qué vale la pena aprender de cada uno, y te dice qué proyectos de código abierto están despegando últimamente y qué merece la pena aprender de cada cual. El «Informe Presidencial» de cada mañana se envía automáticamente al chat privado y al canal de Telegram (añade el Bot como administrador del canal y se reconoce automáticamente, sin configuración).

Un único archivo `worker.js`, cero dependencias, datos almacenados en KV. Panel oscuro: fondo casi negro + verde/cian neón + fuente monoespaciada + textura de líneas de escaneo + marquesina.

## Funciones

- **Once canales de inteligencia** (3 añadidos en v2 y 2 más en v3; cada barrido realiza 11 llamadas a la API de búsqueda de GitHub en total, muy por debajo del límite de 50 subpeticiones del plan gratuito)
1. `surge` Nuevos en auge: creados en los últimos 30 días, stars>50
2. `trending-week` Tendencias de la semana: proyectos populares consolidados con actividad en los últimos 7 días, stars>5000
3. `ai-agent` AI/AGENT: palabras clave ai-agent / llm / mcp
4. `workers` Edge/Bots: cloudflare-workers / serverless / telegram-bot
5. `media` Generación multimedia: comfyui / image-generation / text-to-speech
6. `devtools` Herramientas de desarrollo: developer-tools / browser-automation / playwright
7. `security` Seguridad informática · equipo rojo · SRC: cybersecurity / red team / bug bounty / penetration-testing / vulnerability, stars>200, con actividad en los últimos 90 días
8. `skills` Ecosistema Skill: claude-skills / agent-skills / claude-skill (tokens sin comillas), stars>50, con actividad en los últimos 90 días
9. `creator` Kit completo para creadores: short-video / video-editing / ffmpeg / content creation / subtitles / livestream, stars>200
10. `src-hunt` SRC · caza de vulnerabilidades (nuevo en v3): bug-bounty / 漏洞挖掘 / vulnerability-scanner / vulnerability-hunting, stars>30, con actividad en los últimos 90 días
11. `sec-learning` Material de aprendizaje de seguridad (nuevo en v3): pentest / ctf / web-security / cybersecurity-learning / security-roadmap, stars>200, con actividad en los últimos 90 días
- **Lección de sintaxis de búsqueda (verificada en la práctica)**: dentro de un grupo OR entre paréntesis de GitHub Search solo se pueden poner tokens sin comillas; colocar una frase entrecomillada (como `"claude skills"`) dentro de un grupo OR hace que devuelva directamente `total_count=0` (por eso el canal skills de v2 volvió vacío durante una ronda entera). Las frases entrecomilladas solo se pueden usar por separado, fuera de los paréntesis, p. ej. `"bug bounty" tools stars:>100` (54 resultados, funciona bien). Las palabras clave en chino funcionan, p. ej. `漏洞挖掘 stars:>50` (47 resultados).
- **Semillas WATCHLIST bajo vigilancia estrecha**: una lista seleccionada a mano de 23 entradas en la constante `SEEDS` del código (ecosistema Skill: 12 repositorios + 1 sitio externo, Cocoloop; escritura 3; investigación 1; creación de contenido 8; seguridad 2), cada una con una nota de aprendizaje de una línea escrita a mano. El panel tiene una sección exclusiva «WATCHLIST» agrupada por categorías; cuando un barrido encuentra un repositorio con el mismo nombre que una semilla, su tarjeta fusiona los datos en vivo de ★/calor/calificación/incremento de esta ronda; las semillas no encontradas son capturadas en rotación por el «refresco individual de frescura» del barrido (véanse las notas de v5 más abajo), y las que aún no han rotado se etiquetan como «en vigilancia nominal».
- **Comparación por instantáneas**: cada ronda guarda el número de estrellas en una instantánea (KV `intel:prev`); la ronda siguiente calcula el incremento de cada repositorio en la ronda, `starDelta`; el panel muestra una insignia `+N★ esta ronda` y la tabla de auge se ordena por incremento.
- **Análisis basado en reglas** (en el código es la tabla de palabras clave `LEARNING_MAP` + una fórmula ponderada; el panel lo etiqueta honestamente como «análisis basado en reglas»)
- Puntuación de calor 0-100: escala de estrellas 40 + incremento de la ronda 30 + frescura de actividad 20 + actividad de forks 10
- Etiquetas de puntos de aprendizaje: 40 asignaciones de palabras clave (novedad de v2: pentest/red-team→metodología de evaluación de equipo rojo, vulnerability→gestión de vulnerabilidades, bug-bounty→enfoque de pruebas colectivas SRC, osint→inteligencia de fuentes abiertas, skill→patrones de empaquetado de Skills, subtitle→ingeniería de subtítulos, short-video→flujos de trabajo de vídeo corto, etc.)
- Calificaciones: S ≥70, A ≥45, B el resto; cada entrada lleva un veredicto de plantilla de una línea, p. ej. «+320★ en la última ronda; un proyecto en Python que integra el protocolo MCP: merece la pena estudiar cómo integra el protocolo MCP».
- **Taxonomía fina de etiquetas de seguridad** (novedad de v3, `SECURITY_TAG_MAP` en el código): realiza otra ronda de coincidencia de palabras clave de seguridad sobre nombre del repositorio + descripción + topics, y produce etiquetas finas como inyección SQL / XSS / SSRF / RCE / competiciones CTF / inteligencia de fuentes abiertas (OSINT) / análisis de malware / informática forense / defensa de equipo azul / auditoría de código / penetración en redes internas / escalada de privilegios / escaneo de vulnerabilidades / investigación de PoC / análisis post-vulnerabilidad / rutas de aprendizaje / simulacros de defensa contra phishing / ingeniería inversa / fuzzing / DevSecOps, fusionadas y deduplicadas con las etiquetas de puntos de aprendizaje, con un máximo de 6 por repositorio. Las palabras cortas como RCE/PoC se comparan con límites de palabra, para que «source» no se etiquete por error como RCE ni «epoch» como PoC; «learning» solo se etiqueta como ruta de aprendizaje en un contexto de seguridad, para no etiquetar por error los repositorios de machine learning. Todas las etiquetas son categorías orientadas al aprendizaje y la investigación, no guías de explotación.
- **Interacción del panel** (mejorada en v2): barra superior fija con reloj en vivo en hora de Pekín y estado del barrido; los KPI incluyen ahora el número de canales y de semillas; una barra de filtros fija que admite filtrado bidimensional por canal + calificación (S/A/B) y búsqueda; las tarjetas de las clasificaciones muestran rango, barras de calor animadas y un brillo al pasar el cursor; cada tarjeta enlaza directamente a la página del repositorio en GitHub; el botón «Barrer ahora» está limitado a una vez cada 30 minutos.
- **Filtrado por etiquetas y nube de etiquetas** (novedad de v3): cada etiqueta de una tarjeta es un chip clicable; al hacer clic se filtra «Toda la inteligencia» por esa etiqueta (combinado con canal/calificación/búsqueda mediante AND), y una pastilla de etiqueta activa junto a la barra de filtros la borra con un clic; sobre la sección de seguridad hay una nube de «etiquetas populares» con las 15 etiquetas más frecuentes entre los repositorios de los tres canales de seguridad (security/src-hunt/sec-learning); hacer clic en una etiqueta de la nube activa el mismo filtrado.
- **Paginación de Toda la inteligencia** (novedad de v3): la cuadrícula de «Toda la inteligencia» ahora se pagina en el cliente, con 24 elementos por página (la misma convención que DEAL HUB), con botones de anterior/siguiente y números de página (plegados con puntos suspensivos cuando hay muchas páginas); la línea de estado muestra «Página X / Y · N elementos en total (tras el filtrado)»; cualquier cambio de filtro/búsqueda/etiqueta vuelve a la página 1 y recalcula el número de páginas a partir del conjunto filtrado, y al cambiar de página se desplaza automáticamente a la parte superior de la sección «Toda la inteligencia». Cada sección especializada sigue mostrando una lista Top-N sin paginación.

## Interacción del panel (v4)

- **Secciones plegables**: la barra de título de cada sección principal (Tabla de auge, Nuevos populares, sección AI/AGENT, cada sección de canal, Vigilancia estrecha, Toda la inteligencia) es clicable: un clic para plegar y otro para desplegar (un indicador ▼/▶ a la derecha del título muestra el estado, y el despliegue tiene una animación de aparición gradual). La barra de filtros tiene botones de un clic «Desplegar todo / Plegar todo». Por defecto todo está desplegado.
- **Desplegar todo dentro de una sección**: cada sección especializada muestra por defecto solo las 6 primeras tarjetas; cuando hay más, aparece al final un botón «Desplegar todo: N elementos ▾»: clic para verlas todas y luego «Plegar ▴» para restaurar. Es distinto del plegado de secciones: plegar oculta la sección entera (todo lo que hay bajo su título), mientras que «desplegar todo» solo controla cuántas tarjetas se muestran dentro de una sección.
- **Controles de paginación dobles**: los controles de paginación de «Toda la inteligencia» aparecen **tanto encima como debajo** de la cuadrícula (con un llamativo estilo de borde verde); los números de página, anterior/siguiente y la línea de estado comparten un único estado, y usar cualquiera de los dos conjuntos sincroniza el otro; 24 elementos por página, con la vinculación habitual con los filtros de canal/calificación/búsqueda/etiqueta (un cambio de filtro vuelve a la página 1).
- **Informe Presidencial (ventana flotante)**: un botón flotante permanente «📋 Informe Presidencial» en la esquina inferior derecha abre una ventana de informe arrastrable (arrastra por la barra de título, compatible con ratón y pantalla táctil, no se puede arrastrar fuera de la pantalla; — minimizar y ✕ cerrar en la esquina superior derecha, Esc también cierra; en pantallas pequeñas se adapta automáticamente a un ancho de 92vw). El contenido lo genera el servidor a partir de los datos actuales con plantillas de reglas: un resumen de una línea en más una línea de calor de palabras clave,,, (con las etiquetas de seguridad populares),, (aparece cuando un repositorio ha cambiado de nombre), (número de semillas encontradas y la semilla líder); cada elemento enlaza a GitHub. El pie indica la hora de generación y «motor de reglas (no generado por IA)». Los mismos datos del informe también se incrustan en la página como JSON (`#brief-data`) y pueden obtenerse por separado mediante `GET /api/brief`.

## Novedades de v5

- **Rotación de refresco de frescura de semillas**: además de las 11 búsquedas, cada barrido gasta como máximo 3 llamadas más a la API principal de Repos, dedicadas a refrescar las semillas «no encontradas por el barrido de esta ronda». El cursor se guarda en KV `intel:seedcursor` y rota en el orden de la lista de semillas (saltando las ya encontradas), de modo que en unas pocas rondas se rotan todas las semillas no encontradas. Los resultados del refresco se guardan en `intel:seedlive`: nombre completo actual/★/forks/hora de última actividad + marca de tiempo del refresco; la frescura de los datos de una tarjeta de semilla tiene tres niveles: encontrada en vivo por el barrido de esta ronda → refresco individual (la tarjeta lleva la marca «refresco individual» y la hora) → nominal estática. El refresco pasa por `GET /repos/{owner}/{repo}`; un repositorio renombrado se redirige a su nueva dirección y la respuesta es su identidad actual: el panel muestra el nombre actual anotado como «antes X, renombrado», y escribe el id actual de vuelta en `intel:seedids`; las semillas que devuelven 404 se anotan como «sospecha de eliminación / renombramiento sin rastrear». El límite de llamadas a GitHub por barrido es de 11 búsquedas + 3 refrescos = 14 llamadas.
- **Historial de tendencias de temas**: cada barrido agrega los topics de todos los repositorios (por tema: número de repositorios + estrellas acumuladas, conservando solo los 40 primeros por estrellas acumuladas) y lo añade a KV `intel:topichist`, reteniendo solo las 56 instantáneas más recientes (una ronda cada 6 horas ≈ 14 días). Metodología de tendencias: comparar con la instantánea histórica más cercana a hace unas 24 horas para obtener los incrementos de estrellas/repositorios, y calcular las «rondas consecutivas de calentamiento» (contando hacia atrás desde la instantánea más reciente, el número de rondas en las que las estrellas acumuladas aumentaron estrictamente ronda tras ronda). Los 5 temas con mayor incremento positivo de estrellas en 24 h entran en la sección del Informe Presidencial, y la zona de resumen del panel también muestra una línea de tendencias de temas con la misma metodología debajo de la nube de etiquetas. Se oculta automáticamente cuando hay menos de dos rondas de historial.
- **Envío diario del Informe Presidencial a Telegram**: una vez configurados los Secrets, cuando un barrido de Cron tiene éxito y la hora de Pekín ya pasó de las 08:00, el Informe Presidencial (con la misma estructura que la versión web: Situación de hoy / Top 3 en auge / Top 3 por calor / Foco de seguridad / Tendencias de temas / Renombramientos + enlace al panel, en formato HTML, dentro de unos 1800 caracteres) se envía a Telegram. Pueden coexistir varios destinos de envío: `TG_CHAT_ID` (chat privado con el Bot), `TG_CHANNEL_ID` (un canal especificado manualmente, puede ser `@nombredelcanal` o un id numérico `-100…`; desde v5.3 es solo una sobrescritura opcional), además de todos los canales registrados automáticamente en v5.3 (véase el punto siguiente), todos compartiendo `TG_BOT_TOKEN`; si no hay ningún destino, la función se desactiva en silencio. **Atención: al enviar a un canal, el Bot debe ser administrador de ese canal; de lo contrario, Telegram rechazará la publicación.** La restricción de una vez al día se evalúa por destino, con el estado guardado en `intel:briefpush` (desde v5.3, `{date, targets: {"dm"|"ch:<chatId>": {ok,ts}}}`; el formato antiguo de v5.2 y anteriores, `{date, dm, channel}`, se migra automáticamente al leerse, y los registros de éxito migrados siguen bloqueando el destino ese día como de costumbre): un destino que falló puede reintentarse automáticamente en un barrido posterior del mismo día, mientras que un destino que ya tuvo éxito no se reenvía ese día. Activación manual: `POST /api/brief/push` (desde v5.3.1 requiere autenticación, véase más abajo) envía a todos los destinos a la vez (chat privado + canal manual + canales registrados automáticamente), con la limitación calculada por destino (desde v5.3.1, KV `intel:pushmanual` es un mapa `{"dm"|"ch:<chatId>": ts}`: como máximo 1 envío manual por destino en 6 horas; un canal recién registrado no tiene registro de limitación y puede recibir el envío de inmediato, sin esperar a que expire la limitación de otros destinos; una marca de tiempo del antiguo formato global se migra automáticamente al leerse como una marca solo para `dm`); el campo `brief.push` de `GET /api/brief` informa del estado de configuración (`configured: {dm, manualChannel, autoChannels}`, solo conteos, sin títulos de canales ni ids completos) y del resultado del envío de hoy a cada destino.
- **Registro automático de canales (v5.3)**: ya no hay que buscar manualmente el id de un canal para rellenar `TG_CHANNEL_ID`. Después de hacer al Bot del informe **administrador** de cualquier canal, Telegram envía al Webhook una actualización `my_chat_member` y el Worker registra el canal en KV `intel:tgchannels` (`{ "<chatId>": {title, username, type, status, addedTs, updatedTs}}`), convirtiéndolo automáticamente en destino del informe diario y de los envíos manuales; cuando el Bot es degradado a miembro normal, eliminado o expulsado, el canal se marca como `removed` y los envíos se detienen. Los canales en los que el Bot ya era administrador antes de v5.3 no tienen ese evento, así que se registran retroactivamente con su **primer mensaje nuevo** en el canal (una actualización `channel_post`). `TG_CHANNEL_ID` puede seguir coexistiendo como sobrescritura manual junto al registro automático, deduplicado por chat id para enviar una sola copia. En el comando `/stats`, los títulos de los canales registrados automáticamente son **visibles solo para el propietario** (cuando el chat que emite el comando es el propio `TG_CHAT_ID`); los demás solo ven la cantidad.
- **Reintento ante fallos de canal**: cuando la búsqueda de cualquier canal falla (p. ej. un 403 del límite sin autenticación), se reintenta automáticamente una vez tras un intervalo de 2 segundos antes de declararla fallida; los canales reintentados se registran en los metadatos del barrido `meta.retriedChannels`; el número de semillas refrescadas se registra en `meta.seedRefreshed`.
- **Pila fija global**: la barra de título, la fila de etiquetas populares y la barra de filtros (canal/calificación/búsqueda/desplegar-plegar) se han fusionado en una única pila fija (con fondo sólido), de modo que se puede filtrar directamente desde cualquier posición de desplazamiento de la página, en lugar de solo dentro de la sección «Toda la inteligencia»; la propia sección «Toda la inteligencia» conserva únicamente los dos conjuntos de controles de paginación, arriba y abajo.

## Comandos del Bot (v5.2)

El Bot del informe (el mismo Bot que el envío diario) admite comandos de solo lectura: envía un comando al Bot en Telegram y responde; los datos proceden de la misma fuente que el panel (los mismos datos KV) y **todo es de solo lectura, sin ninguna acción de gestión** (no puede activar barridos ni cambiar la configuración).

| Comando | Descripción |
|---|---|
| `/brief` | Informe Presidencial de hoy (el mismo texto que el envío diario) |
| `/surge` | Tabla de auge TOP5 (incremento de estrellas de esta ronda) |
| `/hot` | Tabla de calor TOP5 |
| `/sec` | Foco de seguridad (TOP5 de la familia de seguridad + etiquetas de seguridad populares) |
| `/watchlist` | Estado de la vigilancia estrecha (total de semillas, cobertura de barrido/refresco/estática, TOP5 por estrellas, avisos de sospecha de eliminación y de renombramiento) |
| `/stats` | Estado del barrido (hora del último barrido, canales, novedades de esta ronda, semillas refrescadas, configuración de envíos y fecha del envío más reciente) |
| `/panel` | Enlaces al panel de inteligencia y al JSON del informe |
| `/help` (o `/start`) | Lista de comandos |

Pasos de activación (tres pasos extra sobre la configuración de envíos de v5):

1. Añade al Worker el Secret `TG_WEBHOOK_SECRET`: genera tú mismo una cadena aleatoria. Sin este Secret, `POST /tg/webhook` devuelve directamente 404 y el sistema de comandos queda desactivado; con él, toda petición cuya cabecera `x-telegram-bot-api-secret-token` no coincida recibirá un 403.
2. Registra el Webhook (sustituye `<TOKEN>`, `<SECRET>` y el dominio por los tuyos). **`allowed_updates` debe incluir los tres tipos: `message`, `my_chat_member` y `channel_post`**: el primero es para los comandos, y los dos últimos son la fuente del registro automático de canales de v5.3 (cuando el Bot se convierte en administrador de un canal, o cuando aparece un mensaje nuevo en un canal ya registrado, se registra el canal); si omites los dos últimos, los comandos seguirán funcionando, pero los canales no se registrarán automáticamente:
`curl "https://api.telegram.org/bot<TOKEN>/setWebhook" -d "url=https://<tu-dirección>/tg/webhook" -d "secret_token=<SECRET>" -d "allowed_updates=[\"message\",\"my_chat_member\",\"channel_post\"]"`
3. Registra el menú de comandos: primero obtén la lista con `curl https://<tu-dirección>/api/tg/commands` y pasa el array `commands` devuelto como parámetro `commands` a `setMyCommands`, para que los usuarios vean el menú de comandos al escribir `/` en el cuadro de entrada.

## Ancla de monitoreo: id del repositorio (v4)

Los repositorios se renombran o se transfieren a otros propietarios, así que `full_name` no es un ancla estable. Desde v4, cada registro guarda el `id` numérico de repositorio de GitHub (devuelto tal cual por la API de búsqueda), y la alineación se basa en él:

- La instantánea `intel:prev` cambió al formato con clave de id `{ts, byId: { "<id>": {s: número de estrellas, n: nombre completo en ese momento}}}`. El antiguo formato plano `{full_name: stars}` se migra automáticamente: en la ronda de migración se construye primero una tabla de búsqueda por nombre a partir de la instantánea antigua, para seguir calculando los incrementos como de costumbre, y al final del barrido se escribe el nuevo formato.
- Al alinear por id para calcular un incremento, si el id es el mismo pero el nombre completo ha cambiado, se considera un **renombramiento**: el incremento se conserva, el registro lleva `renamedFrom`, los metadatos del barrido `meta.renames` registran una entrada `{from, to, stars}`, y aparece en la sección del Informe Presidencial.
- Las semillas de vigilancia estrecha guardan además una asignación de ids (KV `intel:seedids`, `{nombre completo de la semilla: id}`, actualizada en cada barrido cuando una semilla se encuentra por nombre o por un id ya conocido): después de que una semilla se renombre, la ronda siguiente seguirá encontrándola por id, y el panel mostrará su nombre completo **actual** y su enlace.

## Pasos de despliegue

1. Crea un namespace KV en la consola de Cloudflare (p. ej. `github-intel-hub-data`).
2. Crea un nuevo Worker y pega en él el texto completo de `worker.js` (o despliega este directorio con wrangler).
3. Vincula el KV al Worker: el nombre de la variable debe ser **`INTEL_KV`**, apuntando al namespace del paso 1.
4. (Opcional) Añade un disparador Cron; se recomienda `17 */6 * * *` (un barrido cada 6 horas; el límite de GitHub sin autenticación es bajo, no lo ejecutes con demasiada frecuencia).
5. (Opcional) Añade el Secret `GITHUB_TOKEN`: rellenarlo con un token de acceso personal de GitHub (basta con lectura de datos públicos) aumenta mucho el límite de la API; sin él también funciona.
6. (Opcional) Envío del Informe Presidencial a Telegram: añade el Secret `TG_BOT_TOKEN` (el token de BotFather) y luego `TG_CHAT_ID` (tu id de chat privado); si quieres usar el endpoint de envío manual `POST /api/brief/push`, añade también el Secret `PUSH_KEY` (genera tú mismo una cadena aleatoria; al llamar, colócala en la cabecera de petición `x-push-key`; sin este Secret, el endpoint se cierra directamente con un 403); los destinos de canal no necesitan configurar el id manualmente: tras activar el Webhook (incluidos `my_chat_member`/`channel_post`) según la sección «Comandos del Bot (v5.2)», basta con hacer al Bot administrador del canal para que se registre automáticamente (v5.3), y `TG_CHANNEL_ID` (el `@nombredeusuario` del canal o un id numérico `-100…`) sirve solo como sobrescritura manual opcional. Al enviar a un canal, el Bot debe ser administrador de ese canal. Si no añades nada de esto, no se enviará nada. Si además quieres activar los comandos del Bot, añade el Secret `TG_WEBHOOK_SECRET` y registra el Webhook y el menú de comandos según la sección «Comandos del Bot (v5.2)».
7. Abre la dirección del Worker y haz clic en «Barrer ahora» para obtener el primer lote de datos; o `curl -X POST https://<tu-dirección>/api/refresh`.

## API

| Ruta | Descripción |
|---|---|
| `GET /` | Panel de inteligencia (HTML) |
| `GET /api/repos` | El lote más reciente de repositorios en JSON (incluye heat/grade/learnTags/verdict/starDelta), con los datos fusionados de las semillas `watchlist` adjuntos |
| `GET /api/watchlist` | La lista de semillas de vigilancia estrecha en JSON (incluye la categoría de cada entrada, su nota de aprendizaje escrita a mano y los datos de coincidencia en vivo `live`; `null` cuando no hay coincidencia) |
| `GET /api/stats` | Metadatos del barrido más reciente (hora, conteos por canal, errores, eventos de renombramiento `renames`) |
| `GET /api/brief` | El Informe Presidencial en JSON (los mismos datos que la ventana flotante del panel: situación, Top 3 en auge / por calor, foco de seguridad/Skill, renombramientos, calor de palabras clave, tendencias de temas, actividad de la vigilancia), con el estado de envíos `brief.push` adjunto (conteos `configured: {dm, manualChannel, autoChannels}` y resultados de hoy por destino; sin títulos de canales ni ids completos) |
| `POST /api/brief/push` | Enviar manualmente el Informe Presidencial a los destinos de TG (chat privado + canal manual + canales registrados automáticamente). Requiere el Secret `PUSH_KEY`: sin configurar devuelve 403 `status: "push_disabled"`; una cabecera de petición `x-push-key` ausente o incorrecta devuelve 401 `status: "unauthorized"` (no envía ni escribe marcas de limitación); tras superar la autenticación, se aplica una limitación de 6 horas por destino, solo se envía a los destinos no limitados, y la respuesta incluye `targets` (las claves de destino enviadas esta vez) y `skipped` (las claves de destino omitidas por limitación); sin destinos devuelve `status: "not_configured"` |
| `GET /api/tg/commands` | La lista de comandos del Bot en JSON (para `setMyCommands`, 8 comandos) |
| `POST /tg/webhook` | Punto de entrada del Webhook de Telegram (comandos de solo lectura del Bot + registro automático de canales; requiere el Secret `TG_WEBHOOK_SECRET`: 404 si no está configurado, 403 con un secreto incorrecto) |
| `POST /api/refresh` | Activar manualmente un barrido; las llamadas repetidas en 30 minutos se limitan (devuelve `throttled: true`) |
| Cron `scheduled()` | Barridos programados, no sujetos a la limitación manual |

Claves KV: `intel:latest` (datos más recientes), `intel:prev` (instantánea de estrellas de la ronda anterior; formato con clave de id desde v4), `intel:meta` (metadatos del barrido), `intel:seedids` (asignación de ids de repositorio de las semillas), `intel:seedcursor` (cursor de rotación del refresco de semillas), `intel:seedlive` (resultados del refresco de semillas), `intel:topichist` (instantáneas del historial de tendencias de temas, las 56 más recientes), `intel:briefpush` (estado del envío diario del informe; desde v5.3, `{date, targets}` registrado por clave de destino), `intel:pushmanual` (limitación de envíos manuales; desde v5.3.1, un mapa por destino `{"dm"|"ch:<chatId>": ts}`, con el formato global antiguo migrado al leerse), `intel:tgchannels` (la tabla de canales registrados automáticamente, novedad de v5.3).

## Notas de honestidad de los datos

- La única fuente de datos son los resultados públicos de la API de búsqueda de GitHub; el orden y los criterios de inclusión los decide GitHub; las consultas de los canales son reglas de palabras clave, no el Trending oficial de GitHub.
- **Los incrementos de estrellas necesitan al menos dos rondas de barrido**: en la primera ronda el incremento de todos los repositorios está vacío y el análisis escribe «recién incorporado a la base de inteligencia»; solo a partir de la segunda ronda hay un `+N★`.
- El límite sin autenticación es muy bajo (la API de búsqueda permite unas 10 llamadas/minuto, además de una cuota por hora); 11 llamadas en una ronda no son problema, pero no actualices manualmente con alta frecuencia: el código ya aplica una limitación de 30 minutos.
- Cuando la captura de un canal falla, ese canal se marca como anómalo en la marquesina del panel y se conservan los datos de la ronda anterior de ese canal, en lugar de borrar todo el conjunto de datos; si fallan todos los canales, no se sobrescriben los datos existentes.
- El análisis, las calificaciones y los puntos de aprendizaje son todos productos de reglas y pueden fallar (por ejemplo, repositorios que meten palabras clave a la fuerza en su descripción); son solo una referencia para filtrar y no constituyen una garantía de ninguna conclusión de «merece la pena aprenderlo».
- KV es un almacén de consistencia eventual; en las pocas decenas de segundos posteriores a la escritura de un barrido, el panel puede leer brevemente datos antiguos: es un fenómeno normal.
