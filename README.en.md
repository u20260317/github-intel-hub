A "hacker intel center"-style dashboard running on Cloudflare Workers: it sweeps trending GitHub repositories on a schedule, uses a **rule engine** (not AI) to score their momentum and annotate what is worth learning from each, and tells you which open-source projects are surging lately and what each is worth learning. Every morning's "Presidential Briefing" is automatically pushed to a Telegram DM and channel (add the Bot as a channel admin and it is recognized automatically — zero configuration).

A single `worker.js` file, zero dependencies, data stored in KV. Dark dashboard: near-black background + neon green/cyan + monospace font + scanline texture + marquee ticker.

## Features

- **Eleven intel channels** (3 added in v2, 2 more in v3; each sweep makes 11 GitHub Search API calls in total, far below the free plan's 50-subrequest limit)
1. `surge` Surging newcomers: created within the last 30 days, stars>50
2. `trending-week` Trending this week: established popular projects pushed within the last 7 days, stars>5000
3. `ai-agent` AI/AGENT: ai-agent / llm / mcp keywords
4. `workers` Edge/Bots: cloudflare-workers / serverless / telegram-bot
5. `media` Multimedia generation: comfyui / image-generation / text-to-speech
6. `devtools` Developer tools: developer-tools / browser-automation / playwright
7. `security` Security · red team · SRC: cybersecurity / red team / bug bounty / penetration-testing / vulnerability, stars>200, pushed within the last 90 days
8. `skills` Skill ecosystem: claude-skills / agent-skills / claude-skill (unquoted tokens), stars>50, pushed within the last 90 days
9. `creator` Content-creator toolkit: short-video / video-editing / ffmpeg / content creation / subtitles / livestream, stars>200
10. `src-hunt` SRC · bug hunting (new in v3): bug-bounty / 漏洞挖掘 / vulnerability-scanner / vulnerability-hunting, stars>30, pushed within the last 90 days
11. `sec-learning` Security learning resources (new in v3): pentest / ctf / web-security / cybersecurity-learning / security-roadmap, stars>200, pushed within the last 90 days
- **Query syntax lesson (verified in practice)**: inside a GitHub Search OR parenthesized group you can only put unquoted tokens; putting a quoted phrase (such as `"claude skills"`) inside an OR group makes it return `total_count=0` directly (this is why the v2 skills channel came back empty for an entire round). Quoted phrases can only be used standalone, outside the parentheses, e.g. `"bug bounty" tools stars:>100` (54 results, works fine). Chinese keywords work, e.g. `漏洞挖掘 stars:>50` (47 results).
- **WATCHLIST seeds under close monitoring**: a hand-picked list of 23 entries in the `SEEDS` constant in the code (Skill ecosystem 12 repos + 1 external site, Cocoloop; writing 3; research 1; content creation 8; security 2), each with a hand-written one-line learning note. The panel has a dedicated "WATCHLIST" section grouped by category; when a sweep hits a repository with the same name as a seed, its card merges in the live ★/heat/grade/this-round delta; seeds not hit are fetched on rotation by the sweep's "individual freshness refresh" (see the v5 notes below), and seeds not yet rotated to are labeled "named monitoring".
- **Snapshot comparison**: each round stores star counts in a snapshot (KV `intel:prev`); the next round computes each repository's delta for the round, `starDelta`; the panel shows a `+N★ this round` badge, and the surge leaderboard is sorted by delta.
- **Rule-based analysis** (in the code this is the `LEARNING_MAP` keyword table + a weighted formula; the panel honestly labels it "rule-based analysis")
- Heat score 0-100: star scale 40 + this-round delta 30 + push freshness 20 + fork activity 10
- Learning-point tags: 40 keyword mappings (new in v2: pentest/red-team→red-team assessment methodology, vulnerability→vulnerability management, bug-bounty→SRC crowdsourced-testing approach, osint→open-source intelligence, skill→Skill packaging patterns, subtitle→subtitle engineering, short-video→short-video workflows, etc.)
- Grades: S ≥70, A ≥45, B for the rest; each entry carries a one-line template verdict, e.g. "+320★ in the latest round; a Python project integrating the MCP protocol — worth studying how it integrates the MCP protocol."
- **Fine-grained security tag taxonomy** (new in v3, the `SECURITY_TAG_MAP` in the code): runs another round of security-keyword matching over repository name + description + topics, producing fine-grained tags such as SQL injection / XSS / SSRF / RCE / CTF competitions / open-source intelligence (OSINT) / malware analysis / digital forensics / blue-team defense / code auditing / internal-network penetration / privilege escalation / vulnerability scanning / PoC research / vulnerability write-ups / learning paths / phishing-defense drills / reverse engineering / fuzzing / DevSecOps, merged and deduplicated with the learning-point tags, capped at 6 per repository. Short words like RCE/PoC are matched on word boundaries, so "source" is not mislabeled RCE and "epoch" is not mislabeled PoC; "learning" is only tagged as a learning path in a security context, so machine learning repositories are not mislabeled. All tags are learning/research-oriented categories, not exploitation guides.
- **Panel interactions** (upgraded in v2): a sticky top bar with a live Beijing-time clock and sweep status; KPIs now include channel count and seed count; a sticky filter bar supporting two-dimensional filtering by channel + grade (S/A/B) plus search; leaderboard cards show rank, animated heat bars, and a hover glow; every card links straight to the GitHub repository page; the "Sweep now" button is throttled to once per 30 minutes.
- **Tag filtering and tag cloud** (new in v3): every tag on a card is a clickable chip; clicking filters "All Intel" by that tag (combined with channel/grade/search via AND), and an active-tag pill next to the filter bar clears it in one click; above the security section there is a "hot tags" cloud — the top 15 tags by frequency across the repositories of the three security channels (security/src-hunt/sec-learning); clicking a tag in the cloud triggers the same filtering.
- **Pagination for All Intel** (new in v3): the "All Intel" grid is now client-side paginated at 24 items per page (the same convention as DEAL HUB), with previous/next and page-number buttons (collapsed with an ellipsis when there are many pages); the status line shows "Page X / Y · N items in total (after filtering)"; any filter/search/tag change returns to page 1 and recomputes the page count from the filtered set, and turning a page scrolls back to the top of the "All Intel" section. Each dedicated section still shows a Top-N list without pagination.

## Panel Interactions (v4)

- **Collapsible sections**: the title bar of every major section (Surge Leaderboard, Hot Newcomers, AI/AGENT section, each channel section, Watchlist, All Intel) is clickable — click once to collapse, again to expand (a ▼/▶ indicator on the right of the title shows the state, and expanding has a fade-in transition animation). The filter bar has one-click "Expand all / Collapse all" buttons. Everything is expanded by default.
- **Expand all within a section**: each dedicated section shows only the first 6 cards by default; when there are more, an "Expand all N items ▾" button appears at the bottom — click to see them all, then "Collapse ▴" to restore. This is different from section collapsing: collapsing folds away the whole section (everything under its title), while "expand all" only controls how many cards are shown inside a section.
- **Dual pagination controls**: the "All Intel" pagination controls appear **both above and below** the grid (in a prominent green-border style); page numbers, previous/next, and the status line share one state, and using either set syncs the other; 24 items per page, fully linked with channel/grade/search/tag filtering as usual (a filter change returns to page 1).
- **Presidential Briefing (floating window)**: a persistent "📋 Presidential Briefing" floating button in the bottom-right corner opens a draggable briefing window (drag by the title bar, mouse and touch supported, cannot be dragged off-screen; — minimize and ✕ close in the top-right corner, Esc also closes; on small screens it automatically adapts to 92vw wide). The content is generated server-side from the current data using rule templates: a one-line summary in plus a line of keyword heat,,, (including hot security tags),, (appears when a repository has been renamed), (number of seeds hit and the leading seed) — every item is clickable through to GitHub. The footer notes the generation time and "rule engine (not AI-generated)". The same briefing data is also embedded in the page as JSON (`#brief-data`) and can be fetched separately via `GET /api/brief`.

## What's New in v5

- **Seed freshness rotation**: in addition to the 11 searches, each sweep spends at most 3 more core Repos API calls dedicated to refreshing the seeds "not hit by this round's sweep". The cursor is stored in KV `intel:seedcursor` and rotates in seed-list order (skipping seeds already hit), so all unhit seeds get rotated through within a few rounds. Freshness results are stored in `intel:seedlive`: current full name/★/forks/last-push time + freshness timestamp; a seed card's data freshness has three levels — hit live by this round's sweep → individually refreshed (the card carries an "individually refreshed" marker and time) → statically named. The freshness refresh goes through `GET /repos/{owner}/{repo}`; a renamed repository is redirected to its new address and the response is its current identity: the panel shows the current name annotated with "formerly X, renamed", and writes the current id back to `intel:seedids`; seeds returning 404 are annotated "suspected deleted / rename untracked". GitHub calls per sweep are capped at 11 searches + 3 freshness refreshes = 14 calls.
- **Topic trend history**: each sweep aggregates the topics of all repositories (per topic: repository count + cumulative stars, keeping only the top 40 by cumulative stars) and appends it to KV `intel:topichist`, retaining only the most recent 56 snapshots (one round every 6 hours ≈ 14 days). Trend methodology: compare against the historical snapshot closest to about 24 hours ago for star/repository-count deltas, and compute the "consecutive heating rounds" (counting back from the latest snapshot, the number of rounds in which cumulative stars strictly increased round over round). The top 5 topics by positive 24h star delta go into the Presidential Briefing's, and the panel's overview area also shows a line of topic trends in the same methodology below the tag cloud. Automatically hidden when there are fewer than two rounds of history.
- **Daily Telegram push of the Presidential Briefing**: once the Secrets are configured, when a Cron sweep succeeds and Beijing time is past 08:00, the Presidential Briefing (same structure as the Web version: Today's Situation / Top 3 Surging / Top 3 by Heat / Security Focus / Topic Trends / Rename Activity + panel link, in HTML format, within roughly 1800 characters) is pushed to Telegram. Multiple push targets can coexist: `TG_CHAT_ID` (Bot DM), `TG_CHANNEL_ID` (a manually specified channel, can be `@channelname` or a `-100…` numeric id; since v5.3 it is only an optional override), plus all channels auto-registered in v5.3 (see the next item), all sharing `TG_BOT_TOKEN`; with no targets at all, the feature silently turns off. **Note: when pushing to a channel, the Bot must be an admin of that channel, otherwise Telegram will refuse to post.** The once-a-day gate is judged per target, with state stored in `intel:briefpush` (since v5.3, `{date, targets: {"dm"|"ch:<chatId>": {ok,ts}}}`; the pre-v5.2 legacy format `{date, dm, channel}` is automatically migrated on read, and migrated success records still gate that day's target as usual): a target that failed can be retried automatically by a later sweep the same day, while a target that succeeded is not resent that day. Manual trigger: `POST /api/brief/push` (authentication required since v5.3.1, see below) pushes to all targets at once (DM + manual channel + auto-registered channels), with throttling computed per target (since v5.3.1, KV `intel:pushmanual` is a `{"dm"|"ch:<chatId>": ts}` map — at most one manual push per target within 6 hours; a newly registered channel has no throttle record and can be topped up immediately, without waiting for other targets' throttles to expire; a legacy global-format timestamp is automatically migrated on read into a stamp for `dm` only); the `brief.push` field of `GET /api/brief` reports the configuration status (`configured: {dm, manualChannel, autoChannels}`, counts only — no channel titles or full ids) and today's push result for each target.
- **Automatic channel registration (v5.3)**: no more manually looking up a channel id to fill in `TG_CHANNEL_ID`. After you make the briefing Bot an **admin** of any channel, Telegram sends the Webhook a `my_chat_member` update, and the Worker registers the channel into KV `intel:tgchannels` (`{ "<chatId>": {title, username, type, status, addedTs, updatedTs}}`), automatically making it a target of the daily briefing and manual pushes; when the Bot is demoted to a regular member, removed, or kicked, the channel is marked `removed` and pushes stop. Channels where the Bot was already an admin before v5.3 have no such event, so they are registered retroactively by their **first new post** in the channel (a `channel_post` update). `TG_CHANNEL_ID` can still coexist as a manual override alongside auto-registration, deduplicated by chat id so only one copy is sent. In the `/stats` command, the titles of auto-registered channels are **visible only to the owner** (when the chat issuing the command is `TG_CHAT_ID` itself); everyone else sees only the count.
- **Retry on channel failure**: when any channel's search errors (e.g. a 403 from the unauthenticated rate limit), it automatically retries once after a 2-second interval before being judged failed; retried channels are recorded in the sweep metadata `meta.retriedChannels`; the number of seeds refreshed is recorded in `meta.seedRefreshed`.
- **Global sticky stack**: the title bar, hot-tag row, and filter bar (channel/grade/search/expand-collapse) have been merged into a single sticky stack (with a solid background), so you can filter directly from any scroll position on the page instead of only within the "All Intel" section; the "All Intel" section itself keeps only the two sets of pagination controls, top and bottom.

## Bot Commands (v5.2)

The briefing Bot (the same Bot as the daily push) supports read-only commands: send a command to the Bot in Telegram and it answers; the data comes from the same source as the panel (the same KV data), and **everything is read-only — no management actions of any kind** (it cannot trigger a sweep or change configuration).

| Command | Description |
|---|---|
| `/brief` | Today's Presidential Briefing (the same text as the daily push) |
| `/surge` | Surge leaderboard TOP5 (this round's star delta) |
| `/hot` | Heat leaderboard TOP5 |
| `/sec` | Security focus (security family TOP5 + hot security tags) |
| `/watchlist` | Watchlist status (total seeds, sweep/freshness/static coverage, TOP5 by stars, suspected-deletion and rename notices) |
| `/stats` | Sweep status (last sweep time, channels, this round's new additions, seeds refreshed, push configuration and most recent push date) |
| `/panel` | Links to the intel panel and the briefing JSON |
| `/help` (or `/start`) | Command list |

Setup steps (three extra steps on top of the v5 push configuration):

1. Add the Secret `TG_WEBHOOK_SECRET` to the Worker: generate a random string yourself. Without this Secret, `POST /tg/webhook` returns 404 directly and the command system is effectively off; with it, any request whose `x-telegram-bot-api-secret-token` header doesn't match it gets a 403.
2. Register the Webhook (replace `<TOKEN>`, `<SECRET>`, and the domain with your own). **`allowed_updates` must include all three types — `message`, `my_chat_member`, `channel_post`**: the first is for commands, the latter two are the source of v5.3's automatic channel registration (when the Bot is made a channel admin, or when a new post appears in an already-registered channel); if you leave out the latter two, commands still work, but channels will not auto-register:
`curl "https://api.telegram.org/bot<TOKEN>/setWebhook" -d "url=https://<your-address>/tg/webhook" -d "secret_token=<SECRET>" -d "allowed_updates=[\"message\",\"my_chat_member\",\"channel_post\"]"`
3. Register the command menu: first fetch the list with `curl https://<your-address>/api/tg/commands`, then pass the returned `commands` array as the `commands` parameter to `setMyCommands`, so users see the command menu when they type `/` in the input box.

## Monitoring Anchor: Repository id (v4)

Repositories get renamed or transferred to other owners, so `full_name` is not a stable anchor. Since v4, every record stores the GitHub numeric repository `id` (returned as-is by the Search API), and alignment is based on it:

- The snapshot `intel:prev` switched to an id-keyed format `{ts, byId: { "<id>": {s: star count, n: full name at the time}}}`. The old flat `{full_name: stars}` format is automatically migrated: in the migration round, a lookup table is first built from the old snapshot by name so deltas are still computed as usual, and the new format is written back at the end of the sweep.
- When aligning by id to compute a delta, if the id is the same but the full name has changed, it is judged a **rename**: the delta is kept, the record carries `renamedFrom`, the sweep metadata `meta.renames` records an entry `{from, to, stars}`, and it appears in the Presidential Briefing's.
- Watchlist seeds additionally keep an id mapping (KV `intel:seedids`, `{seed full name: id}`, updated each sweep when a seed is hit by name or by an existing id): after a seed is renamed, the next round still hits it by id, and the panel shows its **current** full name and link.

## Deployment Steps

1. Create a KV namespace in the Cloudflare console (e.g. `github-intel-hub-data`).
2. Create a new Worker and paste the full text of `worker.js` into it (or deploy this directory with wrangler).
3. Bind the KV to the Worker: the variable name must be **`INTEL_KV`**, pointing at the namespace from step 1.
4. (Optional) Add a Cron trigger; `17 */6 * * *` is recommended (one sweep every 6 hours; the unauthenticated GitHub rate limit is low, so don't run it too often).
5. (Optional) Add the Secret `GITHUB_TOKEN`: filling in a GitHub Personal Access Token (read-only public data is enough) greatly raises the API rate limit; it also runs without it.
6. (Optional) Telegram push of the Presidential Briefing: add the Secret `TG_BOT_TOKEN` (the token from BotFather), then add `TG_CHAT_ID` (your DM id); if you want to use the manual push endpoint `POST /api/brief/push`, also add the Secret `PUSH_KEY` (generate a random string yourself; when calling, put it in the `x-push-key` request header; without this Secret the endpoint is closed with a 403); channel targets need no manual id configuration — after enabling the Webhook (including `my_chat_member`/`channel_post`) per the "Bot Commands (v5.2)" section, making the Bot a channel admin auto-registers it (v5.3), and `TG_CHANNEL_ID` (a channel `@username` or `-100…` numeric id) serves only as an optional manual override. When pushing to a channel, the Bot must be an admin of that channel. If you add none of these, nothing is pushed. If you also want to enable the Bot commands, add the Secret `TG_WEBHOOK_SECRET` and register the Webhook and command menu per the "Bot Commands (v5.2)" section.
7. Open the Worker address and click "Sweep now" to pull the first batch of data; or `curl -X POST https://<your-address>/api/refresh`.

## API

| Route | Description |
|---|---|
| `GET /` | Intel panel (HTML) |
| `GET /api/repos` | The latest batch of repositories as JSON (including heat/grade/learnTags/verdict/starDelta), with the `watchlist` seed merge data attached |
| `GET /api/watchlist` | The watchlist seed list as JSON (including each entry's category, hand-written learning note, and live hit data `live`; `null` when not hit) |
| `GET /api/stats` | Metadata of the most recent sweep (time, per-channel counts, errors, rename events `renames`) |
| `GET /api/brief` | The Presidential Briefing as JSON (the same data as the panel's floating window: situation, Top 3 surging / by heat, security/Skill focus, rename activity, keyword heat, topic trends, watchlist activity), with the `brief.push` push status attached (`configured: {dm, manualChannel, autoChannels}` counts and today's per-target results; no channel titles/full ids) |
| `POST /api/brief/push` | Manually push the Presidential Briefing to the TG targets (DM + manual channel + auto-registered channels). Requires the Secret `PUSH_KEY`: when not configured it returns 403 `status: "push_disabled"`; a missing/wrong `x-push-key` request header returns 401 `status: "unauthorized"` (no push, no throttle stamp written); after authentication passes, a 6-hour throttle is applied per target, only unthrottled targets are pushed, and the response includes `targets` (the target keys pushed this time) and `skipped` (the target keys skipped due to throttling); with no targets it returns `status: "not_configured"` |
| `GET /api/tg/commands` | The Bot command list as JSON (for `setMyCommands`, 8 commands) |
| `POST /tg/webhook` | Telegram Webhook entry point (Bot read-only commands + automatic channel registration; requires the Secret `TG_WEBHOOK_SECRET` — 404 when not configured, 403 on a wrong secret) |
| `POST /api/refresh` | Manually trigger a sweep; repeated calls within 30 minutes are throttled (returns `throttled: true`) |
| Cron `scheduled()` | Scheduled sweeps, not subject to the manual throttle |

KV keys: `intel:latest` (latest data), `intel:prev` (previous round's star snapshot; id-keyed format since v4), `intel:meta` (sweep metadata), `intel:seedids` (seed repository id mapping), `intel:seedcursor` (seed freshness rotation cursor), `intel:seedlive` (seed freshness results), `intel:topichist` (topic trend history snapshots, most recent 56), `intel:briefpush` (daily briefing push state; since v5.3, `{date, targets}` recorded per target key), `intel:pushmanual` (manual push throttle; since v5.3.1, a per-target map `{"dm"|"ch:<chatId>": ts}`, with the legacy global format migrated on read), `intel:tgchannels` (the auto-registered channel table, new in v5.3).

## Data Honesty Notes

- The only data source is public search results from the GitHub Search API; ranking and inclusion criteria are decided by GitHub; the channel queries are keyword rules, not GitHub's official Trending.
- **Star deltas need at least two sweep rounds**: in the first round every repository's delta is empty and the analysis writes "newly added to the intel database"; only from the second round on is there a `+N★`.
- The unauthenticated rate limit is very low (the Search API allows roughly 10 calls/minute, plus an hourly quota); 11 calls in one round is fine, but don't refresh manually at high frequency — the code already enforces a 30-minute throttle.
- When a channel's fetch fails, that channel is flagged as abnormal in the panel marquee and the previous round's data for that channel is carried over, rather than wiping the whole dataset; if all channels fail, existing data is not overwritten.
- The analysis, grades, and learning points are all rule-produced output and can misjudge (for example, repositories that stuff keywords into their descriptions); they are for filtering reference only and are not a guarantee of any "worth learning" conclusion.
- KV is an eventually consistent store; in the few dozen seconds right after a sweep writes, the panel may briefly read old data — this is normal.
